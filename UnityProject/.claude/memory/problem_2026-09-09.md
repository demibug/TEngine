# 问题记录 2026-09-09

## 问题现象

`PreloadRequestRunnerTests.Begin_DedupesOverlappingAddresses_SingleRequestPerAddress` 失败：
`Expected: 2, But was: 0`（FakeResourceModule.Requests.Count 为 0，Begin 未发出任何加载请求）。
同一实现下其余依赖终态回调的 Preload 测试也会连带失败（Progress/AllTerminal 断言）。

## 根因

- EditMode 测试直接运行在**编辑器主域**，`ModuleSystem` 是跨测试共享的静态单例（`_state` 初始为 Running）。
- `PreloadRequestRunner.Begin` 含运行时防御：`if (addresses == null || !ModuleSystem.IsRunning) return;`（PreloadRequestRunner.cs:116）。
- 当编辑器域内会话状态残留为非 Running（如 ShutdownLifecycle 类测试流程后未复位、或编辑器会话残留），Begin 会**静默提前返回**，单测全挂。
- 根本问题：纯单元测试（Fake 资源模块）不应依赖全局单例状态，但未像 `ShutdownLifecycleTests` 那样显式接管会话状态。

## 正确做法（已修复）

- 抽象基类 `ResourceLifecycleTestBase`（PreloadRequestRunnerTests.cs 内）：在 `[SetUp]`/`[TearDown]` 反射调用 `ModuleSystem.ResetForNewSession`（private static，`[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]`），确保测试运行于 Running 会话且不污染后续测试。
- `PreloadRequestRunnerTests`、`AssetsReferenceTests` 均继承该基类（`AssetsReference.Ref` 同样检查 `IsRunning`，AssetsReference.cs:375）。
- 该模式与 `ShutdownLifecycleTests.cs`（ResetForNewSessionMethod 反射）一致。
- 实现侧的 `ModuleSystem.IsRunning` 防御语义保留不动（关闭期间不得发起新预热是设计意图）。

## 建议修正 / 推广

- 凡是测试目标代码路径中读取 `ModuleSystem.IsRunning` / `State` 的 EditMode 单测，都必须用会话重置基类（或 SetUp/TearDown 反射重置），否则测试结果依赖编辑器域的历史状态，呈"偶现/连带失败"。
- 新建 EditMode 单测文件时优先继承 `ResourceLifecycleTestBase`（ResourceLifecycle 域内）或复制其模式。

## 问题二（同日补充）：EditMode 下普通 MonoBehaviour 的 OnDestroy 不会执行

### 问题现象

修复会话状态后，`AssetsReferenceTests.MaterialBindings_RegisterOriginalAndUnloadEachRendererReference` 失败：
`Expected: 2, But was: 0`（DestroyImmediate 两个绑定对象后 UnloadCallCount 为 0，Ref 本身未抛异常）。

### 根因

- `AssetsReference` 是普通 MonoBehaviour（仅 `[DisallowMultipleComponent]`，无 `ExecuteAlways`）。
- **EditMode 下 Unity 只为 `ExecuteInEditMode/ExecuteAlways` 脚本执行事件函数**（Awake/OnEnable/OnDestroy 等）；
  普通脚本在编辑器域中 `DestroyImmediate` 后不会收到 `OnDestroy`，`ReleaseInternal` 无人触发。
- 同文件 `InactiveNeverActivatedReference_IsReleasedByFallbackSweep` 能通过，正是因为它显式调用了
  `AssetsReference.ReleaseDestroyedReferences()`（生产环境由 `ResourceModule.Update` 轮询的补偿扫描）。
- 真实 `OnDestroy` 归还路径已由 PlayMode 套件覆盖（`ResourceLifecyclePlayModeTests`，`Object.Destroy` + `yield return null`）。

### 正确做法（已修复）

- EditMode 测试断言"销毁→归还"语义时，`DestroyImmediate` 后显式调用 `AssetsReference.ReleaseDestroyedReferences()`。
- 或把需要真实 OnDestroy 的用例放进 PlayMode 套件；不要为了测试给运行时组件加 `[ExecuteAlways]`。

### 建议修正 / 推广

- EditMode 测试永远不要依赖普通 MonoBehaviour 的任何事件函数（Awake/Start/OnEnable/OnDestroy）。
  需要验证这些回调语义时：改用显式补偿/手动触发入口，或写成 PlayMode 测试。

## 问题三（同日补充）：LogAssert 正则与真实模块日志消息脱节

### 问题现象

PlayMode `AssetsReference_ForeignEntryRelease_ThrowsButContinuesOthers` 报
"Unhandled log message: '[Error] ... UnloadAsset failed during cleanup: ...'"——
测试里 `LogAssert.Expect(LogType.Error, new Regex("release .* failed"))` 未匹配到实际日志。

### 根因

- `ResourceModule.UnloadAsset`（ResourceModule.Pool.cs:75-86）语义变更：**内部捕获**归还异常并记
  `Log.Error("UnloadAsset failed during cleanup: {0}", exception)`，异常不再传播到
  `AssetsReference.ReleaseInternal` 的 catch（故旧消息 `AssetsReference release ... failed` 不再出现）。
- 测试断言的是旧实现的消息路径，属"LogAssert 正则耦合实现日志文案"的脆弱点。
- 另注意：DefaultLogHelper 会给消息加 `<color=red><b>[ERROR] ► </b></color>-` 装饰前缀再交给 Debug.Log，
  LogAssert 用 `Regex.IsMatch`（非锚定），匹配稳定子串即可，不要写 `^...$` 锚定。

### 正确做法（已修复）

- 改为 `LogAssert.Expect(LogType.Error, new Regex("UnloadAsset failed during cleanup"))`。
- 测试语义本身不变：归还异常被记录、其余条目继续归还（SpawnCount 回到 before 仍验证此点）。

## 问题四（同日补充）：PlayMode 测试环境无人驱动 ModuleSystem.Update，轮询兜底永不执行

### 问题现象

PlayMode `DeliveredInactiveDestroy_RefundsOnce_AndManualCompensation_NoDouble` 步骤 1 失败：
未激活实例 `Object.Destroy` 后 spawn 计数不减少（Expected: 1, But was: 2）——"未激活销毁必须归还"的补偿未发生。

### 根因

- 未激活即销毁的已交付实例**不保证触发 `AssetsReference.OnDestroy`**，生产环境由
  `RootModule.Update` 每帧调用 `ModuleSystem.Update`（RootModule.cs:210）→
  `ResourceModule.Update` → `AssetsReference.ReleaseDestroyedReferences()` 补偿扫描兜底（ResourceModule.cs:69）。
- `ResourceLifecyclePlayModeTests` 是手动引导（`ModuleSystem.GetModule` + `Initialize`，无 GameEntry/RootModule），
  **`ModuleSystem.Update` 从未被驱动**，扫描永远不跑。
- 其他销毁类测试能过，因为激活实例销毁走 Unity 的 `OnDestroy` 回调，不依赖轮询。
- 取消补偿路径（`InstantiateAndDeliverAsync` → `ReleaseBoundInstanceAndDestroy`，ResourceModule.cs:1610）
  是同步一次性归还，同样不依赖轮询。

### 正确做法（已修复）

- 在依赖轮询兜底的测试步骤中手动 pump 一帧：`ModuleSystem.Update(0.016f, 0.016f)`
  （套件内既有模式，如 ShutdownLifecycle 测试直接调 `ModuleSystem.Update`）。
- 若未来更多测试依赖轮询语义，可考虑在 Bootstrap 中建一个顶级 MonoBehaviour 驱动
  （注意：MonoBehaviour 不能是嵌套类，AddComponent 会失败）。

### 建议修正 / 推广

- PlayMode 手动引导套件中，凡是断言"轮询补偿/对象池自动回收/模块 Update 行为"的用例，
  都必须显式 pump `ModuleSystem.Update`；`AssetAutoReleaseInterval=float.MaxValue` 等设置
  只能关掉回收，不能替你打开轮询。
