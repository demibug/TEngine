# 核心战斗配置覆盖与微信小游戏工程对照

> 审计日期：2026-08-09  
> 审计范围：UnityProject 当前核心战斗链、Luban 源表/生成代码/Provider/运行时，以及 `E:\MyWork\MyTD\TEngine\Origin` 微信小游戏工程。  
> 相关架构总览：[核心战斗模块架构](./核心战斗模块架构.md)

## 1. 先给结论

当前 Unity 核心战斗不是“完全不走配置”，而是采用了如下链路：

```text
Configs/GameConfig/Datas/*.xlsx
        ↓ Luban 生成
Assets/AssetRaw/Configs/bytes/*.bytes + GameProto/GameConfig/Tb*.cs
        ↓ ConfigSystem.Load()
LubanBattleConfigProvider.GetSnapshot()
        ↓
BattleConfigSnapshot
        ↓
BattleRuntimeFactory → BattleManager / WaveManager / UnitFactory / ProjectileFactory
```

当前明确进入生产快照的表只有：`map`、`enemy`、`wave`、`unit`、`unit_level`、`economy`、`projectile`。其中：

- `unit`、`unit_level` 的核心字段基本可以认为已走配置并生效。
- `map`、`enemy`、`wave`、`economy` 只走了部分字段，仍有明显 fallback/硬编码。
- `deck` 表虽然已经存在并生成了 `TbDeck`，但 Provider 没有读取，运行时使用硬编码最简四兵牌组。
- `enemystats` 表已经存在并包含敌人数值，但 Provider 仍使用硬编码数组、速度和接触伤害。
- `boss`、`buff`、`event`、`general`、`item`、`rank`、`result_schema`、`skill`、`weapon_registry`、`weapon_text`、`weapon` 当前没有接入核心 `GameBattle` 配置消费链。
- 微信小游戏工程的原始战斗平衡数据主要在 bundle/JS 常量中；原始外部 JSON 主要是武器、武器字牌、段位和段位附加数据。`Origin/config/*.xlsx` 与 `unity-export/config/*.json` 更像重建/导出配置资产，不能单独证明原始小游戏运行时已经读取这些表。

因此目前最值得优先处理的不是“再建一套表”，而是先把已经存在但不生效的字段接通，并清理 Provider 中已经过时的“缺表/缺字段”判断。

## 2. 审计口径

本文件将状态拆成五种，避免把“字段不存在”和“字段存在但没有消费”混为一谈：

| 状态 | 定义 |
|---|---|
| 已生效 | 源表字段被 Provider 读取，进入 `BattleConfigSnapshot`，并被运行时规则使用。 |
| 部分生效 | 表被读取，但只有部分字段进入快照，或同一域仍混有 fallback。 |
| 未走配置 | 运行时直接使用代码常量、`DeckDefinitions`、Prefab 默认值或 Provider 内硬编码。 |
| 表存在但不生效 | Excel/生成类/bytes 中有字段或表，但 Provider、快照或运行时没有消费它。 |
| 字段/功能缺失 | 当前配置 Schema、生成模型或运行时适配能力无法表达/承载目标数据。 |

“不生效”以 Unity 生产路径为准：`BattleRuntimeFactory` 使用 `ConfigSystem.Instance.Tables` 创建 `LubanBattleConfigProvider`，随后运行时只依赖 `BattleConfigSnapshot`。测试中的 `JsonBattleConfigProvider` 不代表生产配置已经接通。

## 10. 配置源、生成代码和 Provider 的特殊不一致

当前存在几处容易误导排查的旧注释/旧假设：

| 位置 | 旧假设 | 当前实际情况 |
|---|---|---|
| `LubanBattleConfigProvider.cs` 文件头 | `TbEconomy` 缺最大生命、`TbWave` 缺 `skipBoss`、`TbProjectile` 缺 `PrimaryType` | 当前 Unity 源 Excel 和生成类已经有 `economy.playerMaxHealth/opponentMaxHealth`、`wave.skipBoss`、`projectile.primaryType/arrowSpeed` |
| Provider 敌人说明 | `TbEnemy` 缺所有敌人数值 | Unity 已拆出 `enemystats.xlsx`，并生成 `TbEnemyStats`；问题变成 Provider 没接入，而不再是表本身不存在 |
| Provider 牌组说明 | “无 deck 表” | 当前已有 `deck.xlsx`、`TbDeck`、`battle_tbdeck.bytes`，只是 Provider 仍使用硬编码 |
| Provider 投射物说明 | `TbProjectile` 只有 `Types` | 当前源 Excel 至少有 `PrimaryType/ArrowSpeed`，并且源表还出现 `MovementStrategy/HitStrategy`；生成类只部分反映这些字段，属于生成链不同步 |

这些旧注释本身不是运行时行为，但会直接影响后续排查和修复优先级，建议接通配置时同步更新。

## 11. 建议修复顺序

1. **先修已存在字段不生效**：`TbEnemyStats`、`TbDeck`、`TbEconomy` 最大生命、`TbMap` grid/端点、`TbWave.SkipBoss`、`TbProjectile.PrimaryType/ArrowSpeed`。
2. **补齐快照模型字段**：`RewardGold`、`ArrowSpeed`、`ExperienceThresholds`，并决定 `delayTimeMs/maxRounds` 归属 `wave` 还是独立 `battle_rules`。
3. **修复 Luban 源表→生成代码→Provider 的链路一致性**：重点处理 `projectile` 的 `movementStrategy/hitStrategy`，不要只改 Provider 注释。
4. **建立完整配置域**：Boss、Skill、Buff、Weapon、General、AI，并把它们明确接入快照、Factory、Manager 和运行时校验。
5. **最后扩展完整玩法**：108 张牌池、武将字牌合成、AI 难度、武器特殊效果和多投射物类型。

## 12. 结论边界

- 本文是静态源码、源 Excel 表头、生成 C#、Provider 和重建工程资料的交叉审计；没有修改业务代码、配置表或生成代码。
- `Assets/AssetRaw/Configs/bytes` 已确认存在对应二进制资源，但本文没有逐个反序列化每个 bytes 数据行，因此“表中已有”按源 Excel/生成类证据判断；具体 bytes 是否与最新源表同步，仍需单独做生成产物校验。
- 对 Origin 的结论严格区分原始小游戏外部 JSON、重建 JS 行为和重建/导出配置，避免把重建资产当成原始小游戏的真实加载链。
- “未消费”范围是当前 Unity `GameBattle` 核心战斗路径，不代表整个 Unity 工程的其他业务模块没有潜在消费者。
