## 2. 设计目标

1. 按功能拆分 HotFix 程序集，保持依赖单向。
2. 业务功能通过 Module 的接口使用，UI 不直接访问网络、缓存或内部数据。
3. `GameBattle` 负责核心战斗及战斗专属 UI，可以依赖 `GameFUI`，但不依赖 `GamePlay`。
4. `GamePlay` 按背包、任务、商店等非战斗垂直功能组织 `Module`、`Data`、`View`，不依赖 `GameBattle`。
5. `GameCommon` 只承载跨程序集共享的契约、DTO、事件和公共数据。
6. `GameLogic` 作为 HotFix 组合根，负责模块创建、依赖组装和启动。
7. 引入 FairyGUI 作为 UI 底座，由 `GameFUI` 承载 FairyGUI 基础封装与导出 UI 代码；`FUIModule` 对等当前 `UIModule` 的窗口管理职责（窗口堆栈、层级排序、显隐遮挡、生命周期驱动、安全区适配），但不复用 UGUI 实现。`GamePlay` 与 `GameBattle` 各自拥有本领域的 UI 行为代码，二者只通过 `GameCommon` 事件和共享 DTO 通信。

## 3. 程序集依赖

```text
GameLogic
  ├──→ GamePlay → GameFUI → TEngine.Runtime / FairyGUI
  │       └──→ GameCommon → GameProto
  ├──→ GameBattle → GameFUI
  │       └──→ GameCommon → GameProto
  └──→ GameFUI
```

箭头表示“左侧依赖右侧”。`GameLogic` 仍是主入口 DLL，但不应重新堆积所有业务实现。

| 程序集 | 可以依赖 | 不应依赖 |
|---|---|---|
| `GameProto` | Luban 生成运行库、必要的框架类型 | 具体业务模块、UI |
| `GameCommon` | `TEngine.Runtime`、`GameProto` | `GameBattle`、`GamePlay`、具体 UI、网络实现 |
| `GameBattle` | `GameCommon`、必要的 `GameProto`、`GameFUI`、框架类型 | `GamePlay`、`BagModule` 实现、非战斗功能 UI、网络实现 |
| `GamePlay` | `GameCommon`、`GameProto`、`GameFUI`、框架类型 | `GameBattle` 内部实现 |
| `GameFUI` | `TEngine.Runtime`、FairyGUI 运行时 | `GamePlay`、`GameBattle`、`GameLogic` 内部实现、直接修改业务数据 |
| `GameLogic` | `GameCommon`、`GameProto`、`GameBattle`、`GamePlay`、`GameFUI` | 将所有业务实现放入 `GameApp` |

FairyGUI 运行时通过 `Packages` 或 `Plugins` 引入，作为 `GameFUI.asmdef` 的引用程序集；其非热更部分归主包 AOT，`GameFUI.dll` 及其导出 UI 代码归热更。

新增程序集后，必须同时更新 `.asmdef` references、HybridCLR 设置、热更 DLL 配置和 YooAsset DLL 资源。

## 4. GameCommon 职责

`GameCommon` 可以依赖 `GameProto`，用于复用配置表生成的枚举、静态数据类型和协议基础类型；不得包含具体业务实现和运行时状态。

`FUIModule`、`FUIPanel`、`FUIWidget` 等 FairyGUI 专属类型不属于公共业务契约，统一留在 `GameFUI.dll`。`GameCommon` 只保存 `GamePlay` 与 `GameBattle` 都认可的事件、不可变 DTO、枚举和基础数据。

```text
GameCommon/
├── Events/       # 物理上可位于 GamePlay/Module/*/Event，通过 .asmref 归属本程序集
├── Interfaces/   # 跨程序集能力接口
└── GameCommon.asmdef
```

不放入 `GameCommon`：

- `BagModule`、`BattleModule` 等具体实现；
- 可变业务容器和模块内部状态；
- `UIWindow`、`UIWidget`、`GameObject`；
- 网络、缓存、存档等具体实现。

如果 DTO 或事件物理上放在 `GamePlay` 功能目录中，应使用目录级 `.asmref` 编译到 `GameCommon.dll`。`.asmref` 不能放在包含业务实现的目录根部，避免误把实现编入公共程序集。

## 5. 业务 Module 规则

业务 Module 是功能的唯一入口，负责：

- 维护运行时状态；
- 读取 `GameProto` 配置；
- 调用网络、缓存和存档逻辑，必要时使用适配器；
- 校验并修改数据；
- 对外提供查询、命令和快照；
- 在状态变化后发送事件。

调用方不得获得可变的内部集合。接口应优先表达业务能力，例如：

```csharp
bool HasItem(int itemId, int count);
int GetItemCount(int itemId);
BattleLoadoutDto CreateBattleLoadout();
UniTask<bool> UseItemAsync(int itemId, int count);
```

当接口变大时，拆分为只读的 `IBagQuery`、写操作的 `IBagCommand`，再按需要组合为 `IBagModule`。

网络和存储的适配器不是必须独立成目录。只有存在生产实现与测试/离线实现等多个替换实现时，才需要抽出接口；否则先将相关逻辑保留在 Module 内，避免增加没有实际杠杆的间接层。无论是否拆出适配器，都需要明确超时、重试、离线、缓存失效、冲突处理和服务端权威规则。

## 6. GamePlay 与 GameBattle 通信

`GamePlay` 与 `GameBattle` 是同级程序集，禁止互相引用。两者只通过 `GameCommon` 中定义的事件和不可变 DTO 联系，不直接获取对方的 Module、内部状态或 UI 实现。

```text
GamePlay
    └── 根据背包、装备和技能状态创建 BattleLoadoutDto
        └── 发布 BattleLoadoutPrepared 事件

GameBattle
    └── 接收 BattleLoadoutPrepared
        └── 使用不可变快照创建战斗实例
            └── 战斗结束后发布 BattleFinished(BattleResultDto)

GamePlay
    └── 接收 BattleFinished
        └── 执行奖励入账、任务推进和持久化
```

事件名称必须描述已经发生的事实，不使用事件模拟带返回值的跨模块命令。需要立即返回结果的编排由 `GameLogic` 组合根完成；默认通信方式仍为事件和共享 DTO。

战斗开始时读取一次装备、技能和道具快照；战斗过程不应每帧查询背包。战斗结束通过 `BattleResultDto` 和事件通知其他模块。`GameBattle` 可以直接管理战斗 HUD、结算界面等战斗专属 UI，但不得借此访问 `GamePlay` 的实现。

`BattleLoadoutDto`、`BattleResultDto` 等快照应在创建后不可变，不能暴露背包内部数据结构。

## 7. DTO、接口与事件边界

| 类型 | 用途 |
|---|---|
| 公共数据 | 多个程序集共同认可的枚举、常量和基础数据 |
| DTO | 跨模块传递的数据快照，不暴露内部状态 |
| 接口 | 调用并取得结果时使用的能力契约 |
| 事件 | 只通知已经发生的变化，不承担命令和返回值 |
| 模块内部 Data | 放在 `GamePlay/Module/*/Data` 的状态和临时对象，默认属于 `GamePlay.dll` |

事件规则：

- `[EventInterface]` 事件必须在 `GameApp.Entrance` 中先调用 `GameEventHelper.Init()`；
- 跨模块事件和参数归属 `GameCommon.dll`；
- UI 在 `RegisterEvent()` 中使用 `AddUIEvent`；
- 非 UI 模块使用 `GameEventMgr` 管理监听，并在释放时清理；
- 禁止用高频事件驱动每帧刷新，禁止在同名事件回调中递归发送同名事件。

```text
GamePlay/
├── GamePlay.asmdef
└── Module/
    └── BagModule/
        ├── BagModule.cs       # GamePlay.dll，继承 TEngine.Module
        ├── Event/             # 跨程序集契约可通过 .asmref 归属 GameCommon.dll
        ├── Data/              # 默认 GamePlay.dll；共享 DTO/枚举可通过 .asmref 归属 GameCommon.dll
        └── UI/                # 继承 GameFUI 导出代码的实际功能 UI

├── FUIModule.cs              # GameFUI.dll，对等 UIModule 的窗口管理，见 8.1
├── FUIPanel.cs               # 对等 UIWindow，承载 FairyGUI 面板状态与生命周期
├── FUIWidget.cs              # 对等 UIWidget，FairyGUI 子组件
├── WindowAttribute.cs        # [Window] 特性，复用 UIModule 同款元数据契约
├── IFUIResourceLoader.cs     # FairyGUI Package 加载抽象（走 YooAsset）
```

`GamePlay/Module/*/Data` 描述物理位置，`GameCommon.dll` 或 `GamePlay.dll` 描述程序集归属，两者不冲突。只有被 `GameBattle`、`GameFUI` 或其他程序集直接使用的 DTO、枚举和事件参数，才使用目录级 `.asmref` 编译到 `GameCommon.dll`；模块内部的可变运行时数据留在 `GamePlay.dll`。

### 8.1 FUIModule 职责（对等 UIModule）

`FUIModule` 仿照当前 `UIModule` 的窗口管理职责，底座由 UGUI 换成 FairyGUI。二者并存：`UIModule`（UGUI）留在 `GameLogic`，`FUIModule`（FairyGUI）归 `GameFUI`，业务 UI 按需选择继承 `UIWindow` 或 `FUIPanel`。`FUIModule` 必须对等实现以下 `UIModule` 职责：

> 命名落地说明（2026-08-05，任务 7.8）：目标架构表格沿用 `FUIPanel` 命名，
> 但 change `integrate-fairygui-module` 实际落地的顶层窗口基类为 `FUIWindow`（与 `UIWindow` 术语一一对应，
> 详见 `FairyGUI模块接入调研.md` 第 14.2 节）。下文表格中的 `FUIPanel` 在实现中对应 `FUIWindow`；
> `FUIModule` 实际公开入口为 `FUI.ShowAsync<T>`/`FUI.Hide`/`FUI.Close`（详见调研第 15.2 节），
> 而非 `ShowUI`/`ShowUIAsync` 等 UGUI 风格 API。`FUIModule` 当前由 `FUI.RegisterModule(IResourceModule, FUIOptions)`
> 装配，生产 `HotFixModules.Register()` 集成由后续共享热更 change 负责。

| 职责 | UIModule（UGUI）现状 | FUIModule（FairyGUI）对等实现 |
|---|---|---|
| 模块基座 | `Singleton<UIModule>, IUpdate` | `FUIModule : Module, IFUIModule, IUpdateModule`，由 `HotFixModules` 注册并进入更新队列 |
| 根节点常驻 | `GameObject.Find("UIRoot")` + `DontDestroyOnLoad` | 初始化 `GRoot`/`Stage`，FairyGUI 根节点本身常驻，无需手动 `DontDestroyOnLoad` |
| 窗口堆栈 | `List<UIWindow>`，`Push`/`Pop` 按层级插入 | `List<FUIPanel>`，沿用同款按层级插入与 `GetWindow`/`IsContains` |
| 层级深度 | `LAYER_DEEP=2000`/`WINDOW_DEEP=100`，写 `Canvas.sortingOrder` | 同常量语义，写到 FairyGUI `sortingOrder`/`UIPanel` 层级 |
| 显隐与全屏遮挡 | `OnSetWindowVisible`，全屏窗口遮挡下层 | 同款遮挡逻辑，显隐切换走 FairyGUI `visible`/`onStage` |
| 窗口 API | `ShowUI`/`ShowUIAsync`/`ShowUIAsyncAwait`/`CloseUI`/`HideUI`/`CloseAll`/`CloseAllWithOut`/`HasWindow`/`IsAnyLoading`/`GetTopWindow`/`GetUIAsync` | 同名同语义 API，泛型约束改为 `where T : FUIPanel` |
| 窗口实例化 | 反射读 `[Window]` 特性 → `Init(name,layer,fullScreen,assetName,fromResources,hideTimeToClose)` | 复用 `[Window]` 特性与 `Init` 元数据契约，`assetName` 指向 FairyGUI Package/组件名 |
| 资源加载 | `IUIResourceLoader.LoadGameObjectAsync` 加载 Prefab 到 `UIRoot` | `IFUIResourceLoader` 通过 YooAsset 加载 Package 字节再 `UIPackage.AddPackage`，禁止 `Resources.Load` |
| 安全区适配 | `ApplyScreenSafeRect` 基于 `CanvasScaler` 像素换算 | 基于 FairyGUI `GRoot` 坐标系与 `safeArea` 重算，提供同名 `ApplyScreenSafeRect` |
| 错误日志 | `ErrorLogger` 与 `Debugger` 联动 | 沿用 `ErrorLogger` 思路，对接 FairyGUI 异常输出 |
| 帧驱动 | `OnUpdate` 遍历窗口 `InternalUpdate` | `IUpdateModule.Update` 遍历 `FUIPanel.InternalUpdate` |

`FUIModule` 不复用 `UIModule` 的 UGUI 代码，只对等其职责与 API 形态；UGUI 专属类型（`Canvas`/`CanvasScaler`/`GraphicRaycaster`/`RectTransform`）不得出现在 `GameFUI`。

### 8.2 FUIPanel / FUIWidget 对等契约

`FUIPanel` 对等 `UIWindow`，必须提供相同的状态字段与生命周期内部方法，使 `FUIModule` 能用与 `UIModule` 一致的方式驱动：

```text
状态字段对等：
  WindowName / WindowLayer / AssetName / FullScreen / FromResources
  HideTimeToClose / HideTimerId / Depth / Visible / Interactable
  IsLoadDone / IsDestroyed / IsHide / IsPrepare

生命周期内部方法对等：
  Init(name, layer, fullScreen, assetName, fromResources, hideTimeToClose)
  InternalLoad(...)     # 加载 FairyGUI Package/组件，挂到 GRoot 对应层级
  InternalCreate()      # Inject / ScriptGenerator / BindMemberProperty / RegisterEvent / OnCreate（仅一次）
  InternalRefresh()     # OnRefresh（每次 Show）
  InternalUpdate()      # 驱动子 FUIWidget + OnUpdate
  InternalDestroy()     # RemoveAllUIEvent / 子 Widget 销毁 / OnDestroy / 释放 Package
  TryInvoke / CancelHideToCloseTimer / Hide() / Close()
```

`Depth` 与 `Visible` 的实现机制与 UGUI 不同，但对外语义保持一致：

- `Depth`：`UIWindow` 写 `Canvas.sortingOrder`；`FUIPanel` 写 FairyGUI `sortingOrder` 或 `UIPanel` 层级。
- `Visible`：`UIWindow` 切 `gameObject.layer`（`IgnoreRaycast`/`UI`）；`FUIPanel` 切 `GObject.visible` 与是否 `onStage`。
- `Interactable`：`UIWindow` 切 `GraphicRaycaster.enabled`；`FUIPanel` 切 FairyGUI `touchable`。

`FUIWidget` 对等 `UIWidget`，生命周期与 `FUIPanel` 相同（`ScriptGenerator → BindMemberProperty → RegisterEvent → OnCreate → OnRefresh → OnDestroy`），由 `FUIPanel` 在 `InternalUpdate`/`InternalDestroy` 中驱动子 Widget。`AddUIEvent` 在 `RegisterEvent` 中使用，随窗口销毁自动清理，规则与 UGUI 侧一致。

### 8.3 UGUI → FairyGUI 对等映射

| UGUI 概念 | FairyGUI 对等 | 说明 |
|---|---|---|
| `Canvas`/`CanvasScaler`/`Camera` | `GRoot`/`Stage`/`UIConfig` | FairyGUI 自管渲染根，无需 UGUI Canvas |
| `GraphicRaycaster` | `GObject.touchable` / Stage 输入 | 交互性由 `touchable` 表达 |
| UGUI Prefab（`AssetRaw/UI/Prefabs`） | FairyGUI Package + Component（`AssetRaw/FUI`） | `assetName` 指向 Package 内组件 |
| `Canvas.sortingOrder` | `sortingOrder` / `UIPanel` 层级 | 深度排序对等 |
| `gameObject.layer` | `GObject.visible` / `onStage` | 显隐对等 |
| `RectTransform` 安全区 | `GRoot` 坐标系 + `safeArea` | 安全区适配重算 |
| `Resources.Load` | `UIPackage.AddPackage`（YooAsset 提供字节） | 禁止 `Resources.Load`，Package 走 YooAsset |

### 8.4 FairyGUI 资源加载

FairyGUI 不加载 GameObject Prefab，而是加载 Package。`IFUIResourceLoader` 通过 `GameModule.Resource` 的 YooAsset 接口取得 Package 字节/资源，再 `UIPackage.AddPackage` 注册；窗口关闭时按引用计数 `UIPackage.RemovePackage`，避免泄漏。Package 资源统一放在当前工程已有的 `AssetRaw/FUI/` 下，location 等于 Package 名。`FUIModule` 不绕过 YooAsset 直连文件系统。

目录内依赖方向：

```text
GamePlay UI → GameFUI 导出代码
GameBattle UI → GameFUI 导出代码
GamePlay Module → Data / GameCommon 公共接口
GameBattle Module → Data / GameCommon 公共事件和 DTO
GamePlay ↔ GameBattle：禁止程序集引用，只通过 GameCommon 契约通信
```

禁止：

```text
GameBattle → GamePlay / BagModule 具体实现
GamePlay → GameBattle
GameFUI → GamePlay
GameFUI → GameBattle
BagUI → 网络或背包内部数据
GameCommon → 具体功能程序集
```

## 9. GameApp 初始化（目标架构）

目标启动顺序：

```text
GameApp.Entrance(object[])
    1. GameEventHelper.Init()
    2. 保存热更程序集列表
    3. 通过 HotFixModules 注册并初始化热更模块
    4. 按依赖顺序注入跨模块接口和（必要时的）适配器
    5. 所有模块初始化完成后启动主流程和 UI
```

每个业务 Module 需要明确同步初始化、失败、重试和释放行为。释放顺序应与依赖关系相反，且初始化失败不能留下半可用的全局状态。

TEngine 框架模块继续通过 `GameModule.XXX` 访问；不要把所有业务 Module 无限添加到静态 `GameModule`，避免形成新的全局耦合中心。

### 热更模块注册入口（目标实现）

`HotFixModules` 是位于 `GameLogic.dll` 的唯一模块注册入口，由 `GameApp` 调用一次。使用 `HotFixModules` 而不是 `GamePlayModules`，避免名称暗示 `GameBattle` 从属于 `GamePlay`。`GameFUI` 和 `GameBattle` 各提供一个单数命名的生命周期模块：`FUIModule` 和 `BattleModule`。三个模块都继承 `TEngine.Module`，并由 `HotFixModules` 通过 `ModuleSystem.RegisterModule<T>()` 按依赖顺序注册。

```text
GameApp.Entrance(object[])
    1. GameEventHelper.Init()
    2. HotFixModules.Register()
       ├── FUIModule.OnInit()
       ├── BagModule.OnInit()
       └── BattleModule.OnInit()
    3. 启动主流程和 UI
```

示例：

```csharp
// GameLogic.dll：组合并注册各程序集中的模块
public static class HotFixModules
{
    public static void Register()
    {
        FUI.RegisterModule();
        ModuleSystem.RegisterModule<IBagModule>(new BagModule());
        ModuleSystem.RegisterModule<IBattleModule>(new BattleModule());
    }
}

// GameLogic.dll
public static void StartGame()
{
    HotFixModules.Register();
    GameModule.UI.ShowUIAsync<BattleMainUI>();
}
```

注册顺序就是初始化、遍历和更新顺序。GamePlay 和 GameBattle 各自的 UI 可以使用 GameFUI 导出的代码；`FUIModule` 负责 FairyGUI 运行时初始化，`BattleModule` 负责战斗生命周期。二者都由 `HotFixModules` 统一编排，不再拆出独立的 `GameFUIModules` 或 `GameBattleModules`。

`IFUIModule` 与 `FUIModule` 都归 `GameFUI.dll`：前者是公开模块契约和 `ModuleSystem` 注册键，后者继承 `TEngine.Module` 并实现该契约，不沿用 `UIModule` 的 `Singleton` 形态。`IFUIModule` 不放入 `GameCommon`，避免 FairyGUI/FUIPanel 类型泄漏进公共业务契约。

访问入口放在 `GameFUI` 的静态类 `FUI`，而不是位于 `GameLogic.dll` 的 `GameModule`。`HotFixModules` 在启动阶段显式调用一次 `FUI.RegisterModule()`；该方法内部执行 `ModuleSystem.RegisterModule<IFUIModule>(new FUIModule())` 并缓存返回值。业务侧使用 `FUI.Module.ShowUIAsync<XxxFUIPanel>()`。`FUI.Module` 的 getter 不得隐式创建或重复注册；`FUIModule.Shutdown()` 必须清空静态缓存。

`FUIModule.OnInit` 负责 FairyGUI 运行时初始化（`GRoot`/`Stage`/`UIConfig`、`IFUIResourceLoader` 构造、安全区与错误日志接入），须先于依赖它的 GamePlay/GameBattle UI 完成；因此 `Register()` 中 `FUIModule` 排在业务模块之前。`FUI.Module` 与 `GameModule.UI` 并存，分别驱动 FairyGUI 与 UGUI 两套窗口，二者窗口堆栈互不干涉。

业务模块实现 `IUpdateModule` 后会自动进入 TEngine 更新队列，不需要手动调用 `Update()`：

```text
RootModule.Update()
    └── ModuleSystem.Update()
        └── 按注册顺序更新同一 Priority 的业务模块
```

业务模块统一使用默认 `Priority = 0`，不通过不同优先级表达业务依赖。`Register()` 只能在启动阶段调用一次，避免重复注册造成重复初始化和重复更新。`GameLogic.asmdef` 必须显式引用 `GamePlay` 和 `GameBattle`；`GamePlay.asmdef` 与 `GameBattle.asmdef` 都引用 `GameFUI` 和 `GameCommon`，但互不引用。

## 10. HybridCLR 落地清单

启用 `GameCommon`、`GameBattle`、`GamePlay`、`GameFUI` 后，必须验证：

1. `.asmdef` references 和程序集依赖无环；
2. `HybridCLRSettings.asset` 包含所有热更程序集；
3. `UpdateSetting.asset.HotUpdateAssemblies` 包含所有 DLL；
4. DLL 已生成并复制到 `AssetRaw/DLL`；
5. YooAsset 能按正确地址加载 DLL bytes；
6. 依赖程序集先于使用它的程序集加载；
7. AOT 元数据和新增泛型引用已生成；
8. `LogicMainDllName` 仍为 `GameLogic.dll`；
9. 真实构建中能完成 DLL 加载、事件初始化、模块初始化和释放；
10. `GameFUI.dll` 已加入 `HybridCLRSettings` 热更程序集与 `UpdateSetting.HotUpdateAssemblies`，且加载顺序在依赖它的 `GamePlay`、`GameBattle`、`GameLogic` 之前；
11. FairyGUI 运行时非热更，`FairyGUI.dll` 加入 `AOTMetaAssemblies`，并核验新增泛型引用（如 `List<FUIPanel>`、`UniTask<FUIPanel>`）已补全；
12. FairyGUI Package 资源已纳入 YooAsset `AssetRaw/FUI/` 构建与版本清单，`UIPackage.AddPackage` 能按 location 加载。

不能只修改 `.asmdef` 就认为热更拆分完成，必须通过真实构建和运行验证。

## 11. 分阶段落地

### 阶段一：建立公共边界

- 完善 `GameCommon.asmdef`，增加对 `GameProto` 的引用；
- 创建公共事件、DTO 和模块接口；
- 为 `GameLogic`、`GameBattle`、`GamePlay`、`GameFUI` 建立显式程序集引用；
- 为 `GamePlay` 和 `GameBattle` 增加对 `GameFUI` 的程序集引用，二者互不引用；
- 引入 FairyGUI 运行时（`Packages` 或 `Plugins`），`GameFUI.asmdef` 增加 FairyGUI 与 `TEngine.Runtime` 引用；
- 创建 `GameFUI`，由它承载 FairyGUI 基础封装和导出的 UI 代码；
- 仿照 `UIModule` 实现 `IFUIModule`、`FUIModule`（继承 `TEngine.Module`）与 `FUIPanel`/`FUIWidget`/`WindowAttribute`/`IFUIResourceLoader`，对等 8.1/8.2 职责，先搭窗口堆栈与 `ShowUI`/`CloseUI` 骨架；
- 在 `GameFUI` 增加静态访问类 `FUI`，由 `HotFixModules.Register()` 首位调用 `FUI.RegisterModule()`；
- 保持 `GameLogic.dll` 为热更主入口。

### 阶段二：实现功能 Module

- 创建 `GamePlay/Module/BagModule`；
- 将网络、缓存、数据修改和事件发送收拢到 `BagModule`；
- 网络和存储只有在存在多个替换实现时才抽取适配器；
- UI 只依赖 BagModule 的公开接口。

### 阶段三：接入战斗

- `GameBattle` 增加对 `GameFUI` 的引用并承载战斗专属 UI；
- `GameBattle` 与 `GamePlay` 保持同级，禁止互相引用；
- 使用 `GameCommon` 中的不可变战斗快照和事件启动战斗；
- 通过结果 DTO 和事件完成战斗结算及 GamePlay 状态更新。

### 阶段四：完成热更验证

- 更新 HybridCLR、YooAsset 和 AOT 配置；
- 将 `GameFUI` 纳入程序集和 UI 资源构建流程；
- 核验 `FairyGUI.dll` 进入 AOT 元数据、`GameFUI.dll` 进入热更程序集，FairyGUI Package 纳入 YooAsset 版本清单；
- 验证 DLL 加载顺序和运行时依赖；
- 增加程序集、模块生命周期和跨模块通信测试。

## 12. 架构决策摘要

```text
GameProto ：Luban 生成的配置和协议基础类型
GameCommon：依赖 GameProto 的公共事件、DTO、接口和数据
GameLogic ：GameApp、启动编排和组合根
GamePlay  ：背包、任务、商店等功能 Module
GameFUI   ：FairyGUI 基础封装、导出 UI 代码和 FUIModule
IFUIModule：GameFUI 内的公开模块契约和 ModuleSystem 注册键
FUIModule ：对等 UIModule 窗口管理职责，FairyGUI 底座，继承 TEngine.Module
FUI       ：GameFUI 内的 IFUIModule 显式注册与静态访问入口
FairyGUI  ：运行时非热更、进 AOT 元数据，Package 资源走 YooAsset
GameBattle：核心战斗、BattleModule 和战斗专属 UI，与 GamePlay 同级
HotFixModules：GameLogic 组合根中的统一模块注册入口
BagModule ：背包网络、缓存、数据修改和对外能力的唯一入口
```
