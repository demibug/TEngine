# HotFix 架构设计

> 状态：架构讨论落盘版本
>
> 日期：2026-08-03
>
> 范围：HybridCLR 热更程序集、GameCommon 公共契约、GameBattle 核心战斗、GamePlay 功能模块，以及模块之间的数据和事件通信。

## 1. 设计目标

- 将游戏功能拆分到多个 HotFix 程序集，降低单一程序集的耦合。
- 所有功能操作通过对应的 Module 完成，UI 不直接操作网络和数据存储。
- `GameBattle` 只负责核心战斗，不放具体 UI。
- `GamePlay` 承载背包、任务、养成等非核心战斗功能，并按功能组织 `Module`、`Data`、`View`。
- `GameCommon` 承载跨程序集共享的事件、公共数据、DTO 和接口定义。
- 保持程序集依赖单向，避免 `GameBattle` 与 `GamePlay`、`GameLogic` 之间形成循环引用。

## 2. 当前工程约束

当前工程的热更入口仍然是 `GameLogic.dll`：

```text
ProcedureLoadAssembly
    └── 反射获取 GameLogic.dll 中的 GameApp
        └── GameApp.Entrance(object[])
```

因此，`GameLogic` 暂时不能简单地变成纯公共程序集。它仍需要承担：

- `GameApp` 热更入口；
- 热更模块初始化和组合；
- 跨功能模块的启动编排；
- 当前已有的 `GameModule` 和部分公共运行时能力。

后续建议将 `GameLogic` 定位为“HotFix 组合根和主入口”，将真正的公共契约放入 `GameCommon`。

当前还需要注意：

- `GameBattle.asmdef` 和 `GamePlay.asmdef` 目前只是程序集占位文件。
- `UpdateSetting.asset` 当前主要配置了 `GameProto.dll` 和 `GameLogic.dll`。
- 如果启用新的程序集，必须同步 HybridCLR、热更 DLL 资源和 `HotUpdateAssemblies` 配置。
- 当前 `GameLogic` 还包含 `UIModule`、`UIWindow`、`UIWidget` 等 UI 基础设施，后续可以继续保留，也可以独立为客户端运行时程序集。

## 3. 目标程序集关系

推荐依赖关系如下：

```text
                         ┌──────────────────────┐
                         │ GameLogic             │
                         │ GameApp / 组合根       │
                         │ 启动与模块编排         │
                         └──────┬─────────┬─────┘
                                │         │
                     ┌──────────▼──┐ ┌──▼───────────┐
                     │ GameBattle  │ │ GamePlay     │
                     │ 核心战斗     │ │ 功能模块      │
                     │ 无具体 UI    │ │ Bag/Task 等   │
                     └──────┬──────┘ └────┬─────────┘
                            │              │
                            └──────┬───────┘
                                   ▼
                         ┌──────────────────────┐
                         │ GameCommon            │
                         │ 事件 / DTO / 接口      │
                         │ 公共数据 / 常量        │
                         └──────────────────────┘
```

依赖规则：

| 程序集 | 可以依赖 | 不应依赖 |
|---|---|---|
| `GameCommon` | `TEngine.Runtime` 中确实需要的公共类型 | `GameBattle`、`GamePlay`、具体 UI、网络实现 |
| `GameBattle` | `GameCommon`、必要的 `GameProto`、必要的框架 API | `BagModule` 具体类、Bag UI、网络实现 |
| `GamePlay` | `GameCommon`、`GameProto`、必要的框架 API | `GameBattle` 的内部实现、战斗 UI 的内部组件 |
| `GameLogic` | `GameCommon`、`GameProto`、`GameBattle`、`GamePlay` | 将所有业务实现堆回 `GameApp` |

如果 `GamePlay` 需要启动战斗，可以依赖 `GameBattle` 的公开模块接口；反过来，`GameBattle` 不应依赖 `GamePlay`。战斗结果通过 DTO 或事件通知给其他模块。

## 4. GameCommon 的职责

`GameCommon` 只定义跨程序集都认可的契约，不负责具体业务实现。

推荐目录：

```text
GameCommon/
├── Events/
│   ├── IBagEvent.cs
│   ├── IBattleEvent.cs
│   └── IPlayerEvent.cs
├── DTO/
│   ├── BattleLoadoutDto.cs
│   ├── BattleResultDto.cs
│   └── ItemStackDto.cs
├── Interfaces/
│   ├── IBagModule.cs
│   └── 其他跨模块接口
├── Data/
│   ├── 公共枚举
│   ├── 公共常量
│   └── 轻量公共数据定义
└── GameCommon.asmdef
```

这里的目录表示逻辑归属，不强制要求文件物理上位于 `GameCommon/` 文件夹。为了让同一功能的代码保持垂直聚合，`BagModule` 的事件和 DTO 可以物理上放在 `GamePlay/Module/BagModule/` 下，再通过 `.asmref` 将它们编译到 `GameCommon.dll`：

```text
GamePlay/
└── Module/
    └── BagModule/
        ├── BagModule.cs              # GamePlay.dll
        ├── DTO/
        │   ├── GameCommon.DTO.asmref
        │   └── BagItemDto.cs         # GameCommon.dll
        └── Event/
            ├── GameCommon.Event.asmref
            └── IBagEvent.cs          # GameCommon.dll
```

两个 `.asmref` 都引用 `GameCommon.asmdef`。`.asmref` 所在目录及其子目录会编译进目标程序集，因此不能把 `.asmref` 放在 `BagModule/` 根目录，否则 `BagModule.cs` 也会被编译进 `GameCommon.dll`。该方式只改变程序集归属，不改变 C# namespace。

`GameCommon` 必须只依赖 `TEngine.Runtime` 和其他公共程序集；`GamePlay` 可以依赖 `GameCommon`，但 `GameCommon` 不得反向依赖 `GamePlay`。如果事件参数是 DTO，该 DTO 必须和事件契约位于 `GameCommon.dll`，或位于另一个更底层的公共契约程序集，不能只定义在 `GamePlay.dll` 中。

不放入 `GameCommon` 的内容：

- `BagModule`、`BattleModule` 等具体实现；
- `Dictionary` 等业务内部容器；
- `BagUI`、`BattleUI`、`UIWindow`、`GameObject`；
- 网络请求实现、缓存实现、存档实现；
- 只在单个功能内部使用的状态和临时对象。

## 5. Module 设计原则

所有功能操作通过 Module 暴露，Module 是功能的唯一业务入口。

以背包为例：

```text
BagModule
    ├── 网络请求
    ├── 本地缓存
    ├── Luban 配置查询
    ├── 背包数据修改
    ├── 存档和同步
    └── 对外提供查询、命令和快照
```

UI 只调用 `BagModule` 的公开 API，不直接发网络请求，也不直接修改背包数据。

不建议暴露内部数据结构：

```csharp
// 不建议：调用方可以绕过 BagModule 修改内部状态。
Dictionary<int, BagItemData> GetInternalItems();
```

推荐暴露业务能力：

```csharp
bool HasItem(int itemId, int count);
int GetItemCount(int itemId);
BattleLoadoutDto CreateBattleLoadout();
UniTask<bool> UseItemAsync(int itemId, int count);
```

## 6. IBagModule 设计

`IBagModule` 定义在 `GameCommon`，`BagModule` 定义在 `GamePlay` 并实现该接口。

```csharp
public interface IBagModule
{
    UniTask InitializeAsync();

    bool HasItem(int itemId, int count);

    int GetItemCount(int itemId);

    BattleLoadoutDto CreateBattleLoadout();

    UniTask<bool> UseItemAsync(int itemId, int count);
}
```

接口的具体签名以实际业务为准，原则是：

- 查询方法只读，不返回可变内部容器；
- 修改方法由 `BagModule` 负责校验、修改、同步和发事件；
- 网络请求仍然封装在 `BagModule` 内部；
- `GameBattle` 只依赖 `IBagModule` 或更窄的能力接口，不依赖 `BagModule` 具体类型。

当接口逐渐变大时，可以拆分为：

```csharp
public interface IBagQuery
{
    bool HasItem(int itemId, int count);

    BattleLoadoutDto CreateBattleLoadout();
}

public interface IBagCommand
{
    UniTask<bool> UseItemAsync(int itemId, int count);
}

public interface IBagModule : IBagQuery, IBagCommand
{
    UniTask InitializeAsync();
}
```

这样，普通 UI 可以使用完整的 `IBagModule`，而只需要读取战斗装备的模块可以只依赖 `IBagQuery`。

## 7. GameBattle 获取背包数据

推荐通过 `IBagModule` 获取战斗开始时所需的数据，并转换为不可变的战斗快照：

```text
GameLogic / Bootstrap
    ├── 创建或获取 BagModule
    ├── 初始化 BagModule
    ├── 将 BagModule 作为 IBagModule 注入 BattleModule
    └── 启动游戏功能

BattleModule.StartBattle()
    └── IBagModule.CreateBattleLoadout()
        └── 使用 BattleLoadoutDto 创建战斗实例
```

建议 `GameBattle` 在战斗开始时读取一次装备、技能和道具快照，而不是战斗过程中每帧查询背包。

```csharp
public sealed class BattleLoadoutDto
{
    public int WeaponId;
    public int ArmorId;
    public int[] SkillIds;
    public int[] ConsumableItemIds;
}
```

`BattleLoadoutDto` 只描述战斗需要的数据，不暴露背包内部的完整数据模型。

如果战斗过程中确实需要消耗道具，仍然通过 `IBagModule.UseItemAsync` 或更窄的 `IBagCommand` 完成，`GameBattle` 不自行扣除数量，也不直接访问网络。

## 8. DTO、公共数据和事件的边界

三者用途不同：

| 类型 | 作用 | 示例 |
|---|---|---|
| 公共数据 | 多个程序集都认可的基础定义 | `ItemType`、`Quality`、公共枚举 |
| DTO | 在模块之间传递的数据快照 | `BattleLoadoutDto`、`BattleResultDto` |
| 事件 | 通知某件事已经发生 | `OnBagChanged`、`OnBattleFinished` |
| 接口 | 约定某个模块提供的能力 | `IBagModule`、`IBagQuery` |

推荐判断：

```text
需要调用并取得返回结果 → Module / Interface
需要传递一组结构化数据 → DTO
只需要通知发生了变化   → GameEvent
只在模块内部使用        → 模块自己的 Data
```

## 9. 事件通信规则

跨模块事件逻辑上属于 `GameCommon`，物理上可以放在 `GameCommon/Events`，也可以按功能放在 `GamePlay/Module/<功能模块>/Event`，但后者必须通过 `.asmref` 编译到 `GameCommon.dll`。例如：

```text
IBagEvent
    ├── OnBagInitialized
    ├── OnItemChanged
    └── OnBagSyncCompleted

IBattleEvent
    ├── OnBattleStarted
    ├── OnBattleFinished
    └── OnBattleRewarded
```

规则：

- 使用 `[EventInterface]` 的接口事件时，确认 `GameEventHelper.Init()` 在 `GameApp.Entrance` 中最先调用；
- 当事件接口通过 `.asmref` 归属 `GameCommon.dll` 时，`Definition.NameSpace` 使用 `GameCommon`，Source Generator 生成的 `Ixxx_Event`、`Ixxx_Gen` 和 `GameEventHelper` 也归属于 `GameCommon`；
- `GameLogic` 或其他调用方通过 `GameCommon` 引用这些生成类型，不能让 `GameCommon` 反向依赖 `GamePlay`；
- UI 在 `RegisterEvent()` 中使用 `AddUIEvent`，让窗口销毁时自动清理；
- 非 UI 模块使用 `GameEventMgr` 管理监听，并在释放时调用 `Clear()`；
- 事件用于通知，不用于需要返回值的命令调用；
- 不要通过高频事件每帧刷新 UI；
- 不要在同一个事件回调中递归触发同名事件。

## 10. GamePlay 功能目录

`GamePlay` 推荐按垂直功能组织，而不是把所有 Module、View、Data 放在全局目录。事件和 DTO 虽然逻辑上属于 `GameCommon`，也可以通过 `.asmref` 保持在对应功能目录下：

```text
GamePlay/
├── GamePlay.asmdef
└── Module/
    └── BagModule/
        ├── BagModule.cs              # GamePlay.dll
        ├── DTO/
        │   ├── GameCommon.DTO.asmref
        │   ├── BagItemDto.cs         # GameCommon.dll
        │   └── BagStateDto.cs        # GameCommon.dll
        ├── Event/
        │   ├── GameCommon.Event.asmref
        │   └── IBagEvent.cs          # GameCommon.dll
        ├── Data/                     # GamePlay.dll，模块内部状态
        └── View/                     # GamePlay.dll，功能视图
```

`TaskModule`、`ShopModule` 等其他功能模块遵循同样规则：模块实现留在 `GamePlay.dll`，跨程序集共享的 DTO 和事件契约通过各自目录下的 `.asmref` 归属 `GameCommon.dll`。如果一个目录下的全部脚本都应该进入 `GameCommon.dll`，才可以把 `.asmref` 放在该目录的上一级。

目录内的依赖方向：

```text
View → Module / 对外接口 → Data
```

禁止：

```text
BagModule → BagUI
BagData → BagUI
GameBattle → BagUI
```

Luban 生成的静态配置继续放在 `GameProto`，不要和 `BagState` 这类运行时状态混淆。

## 11. GameApp 和模块初始化

`GameApp` 负责组合和启动，不承载具体业务细节。

推荐启动顺序：

```text
GameApp.Entrance(object[])
    1. GameEventHelper.Init()
    2. 保存热更程序集列表
    3. 创建或获取 GamePlay 模块
    4. 初始化 BagModule、BattleModule 等模块
    5. 注入跨模块接口依赖
    6. 启动主流程和 UI
```

示意关系：

```text
BagModule : IBagModule
        │
        └── 注入 BattleModule
                    │
                    └── 仅通过 IBagModule 获取背包能力
```

`GameModule` 当前主要承担 TEngine 框架模块的统一访问，例如资源、音频、场景、计时器和 UI。不要无约束地把所有业务功能都塞入一个越来越大的静态 `GameModule`，否则它会重新成为全局耦合中心。

## 12. HybridCLR 和程序集配置

启用多个 HotFix 程序集后，需要同步：

1. `GameCommon.dll`、`GameBattle.dll`、`GamePlay.dll` 加入 `HotUpdateAssemblies`；
2. `HybridCLRSettings.asset` 的热更程序集定义；
3. DLL 生成和复制到 `AssetRaw/DLL` 的流程；
4. YooAsset 对 DLL bytes 资源的收集；
5. AOT 泛型引用和必要的 `UniTask<自定义 DTO>`、集合泛型补充；
6. 程序集依赖顺序和运行时加载验证；
7. 检查 `GamePlay/Module/*/DTO` 和 `GamePlay/Module/*/Event` 下的 `.asmref` 是否只覆盖公共 DTO 与事件契约，避免误将 Module 实现编译进 `GameCommon.dll`。

`LogicMainDllName` 继续保持为 `GameLogic.dll`，因为主包流程需要从其中查找 `GameApp`。

建议的逻辑依赖顺序为：

```text
GameCommon → GameProto → GameBattle / GamePlay → GameLogic
```

实际 DLL 加载顺序以 HybridCLR 和当前加载器行为验证为准，不能只修改 asmdef 后认为热更已经完成。

## 13. 禁止的依赖和反模式

```text
GameBattle 直接 new BagModule
GameBattle 直接访问 BagModule 内部字典
GameBattle 直接请求网络
BagUI 直接修改背包数据
GameLogic 直接包含所有功能实现
GameBattle ↔ GamePlay 双向引用
GameCommon 引用具体功能程序集
```

正确方式是：

```text
GameBattle → IBagModule / IBagQuery
BagModule → 负责网络、缓存、数据修改
BagUI → 调用 BagModule
GameCommon → 只定义稳定的公共契约
GameLogic → 负责启动、注册和依赖组装
```

## 14. 分阶段落地建议

### 阶段一：建立边界

- 创建 `GameCommon` 程序集；
- 将跨模块事件和公共数据移动到 `GameCommon`；
- 在 `GameCommon` 定义 `IBagModule`；
- 保持现有 `GameLogic.dll` 作为主入口。

### 阶段二：实现背包模块

- 在 `GamePlay/Module/BagModule` 创建 `BagModule`；
- 在 `GamePlay/Module/BagModule/DTO` 和 `GamePlay/Module/BagModule/Event` 分别放置指向 `GameCommon.asmdef` 的 `.asmref`，使 DTO 和事件契约进入 `GameCommon.dll`；
- 由 `BagModule` 接管网络、缓存、数据修改和事件发送；
- UI 只调用 `BagModule` 对外 API；
- 禁止 UI 直接持有内部背包集合。

### 阶段三：接入战斗

- `GameBattle` 只引用 `GameCommon` 的 `IBagModule` 或 `IBagQuery`；
- 由启动层注入 `BagModule`；
- 战斗开始时生成 `BattleLoadoutDto`；
- 战斗结束通过 `BattleResultDto` 和事件通知。

### 阶段四：完善热更拆分

- 将新程序集加入 HybridCLR 和 YooAsset 热更流程；
- 更新 UI 脚本生成路径；
- 检查 AOT 泛型引用；
- 用真实构建和运行流程验证程序集加载、事件初始化和模块生命周期。

## 15. 当前架构决策摘要

```text
GameCommon：公共事件、公共数据、DTO、模块接口
GameLogic ：GameApp、启动编排、组合根
GameBattle：核心战斗，不放具体 UI，不直接访问背包实现
GamePlay  ：背包、任务、商店等功能模块，内部包含 Module/Data/View；功能目录下的 DTO/Event 可通过 .asmref 归属 GameCommon
BagModule ：背包网络、缓存、数据操作和对外能力的唯一入口
IBagModule：定义在 GameCommon，由 BagModule 实现，供其他模块依赖
```

这份文档描述的是目标架构和落地约束，当前代码尚未按全部内容完成重构。
