# 两阶段热更固定入口实施说明

> 两阶段更新只支持固定 `current.json` 入口。
> 本功能只负责客户端消费和本地发布；不会上传远程服务器，也不会自动修改运行时配置资产。

## 1. 功能概览

固定入口模式只需要在 `UpdateSetting` 中配置一次 `current.json` 地址。每次构建使用新的
`ReleaseId`，本地发布器把完整构建产物复制到新的不可变 release 目录，最后原子替换
`current.json`。客户端启动时先读取入口，再只使用该入口选出的 release 下载 descriptor、清单和资源。

`TwoStageReleaseEntryUrl` 必须是以 `/current.json` 结尾的固定入口地址；主、备资源地址是固定身份根，
客户端会追加 `/releases/{ReleaseId}`。工程不再支持直接配置某个 release descriptor。

固定入口的 `ReleaseId` 只能是 1～128 个 ASCII 字母、数字、`-` 或 `_`。点号、路径分隔符、
百分号编码、空白和 URL 都会被拒绝。入口格式版本是独立的 `EntryVersion=1`，不会提高
`TwoStageContractVersion`。

## 2. 配置一次固定入口

在 `TEngine → Settings → TEngine UpdateSettings` 中：

1. 开启 `EnableTwoStageUpdate`。
2. 配置 `TwoStageReleaseEntryUrl`，例如：

   ```text
   https://cdn.example.com/demo-v1/Windows64/default/DefaultPackage/current.json
   ```

3. 将 `TwoStageHostServerUrl` 和 `TwoStageFallbackHostServerUrl` 配置为同一身份的固定资源根，
   例如：

   ```text
   https://cdn.example.com/demo-v1/Windows64/default/DefaultPackage/
   https://backup.example.com/demo-v1/Windows64/default/DefaultPackage/
   ```

入口和资源根必须是绝对 HTTPS URL；仅在开发环境中勾选
`AllowInsecureLoopbackHttp` 后才允许 `127.0.0.1` 或其他 loopback HTTP。固定模式不接受用户信息、
查询参数或 fragment。主备根允许末尾 `/`。

不要把 `ReleaseId` 写进 `UpdateSetting` 的 URL。发布器和客户端会按固定协议生成：

```text
{entry 所在目录}/releases/{ReleaseId}/TwoStageRelease_{ReleaseId}.json
{primary 固定根}/releases/{ReleaseId}/{YooAsset 文件}
{fallback 固定根}/releases/{ReleaseId}/{YooAsset 文件}
```

## 3. 固定发布目录

发布根目录由打包窗口的 `本地发布根目录` 指定。发布器会生成：

```text
{PublishRoot}/
└─ {BasePlayerId}/{Platform}/{Channel}/{PackageName}/
   ├─ current.json
   ├─ .two-stage-publish.lock
   └─ releases/
      └─ {ReleaseId}/
         ├─ TwoStageRelease_{ReleaseId}.json
         ├─ YooAsset 清单、版本和哈希文件
         ├─ bundle 文件
         └─ 原 OutputPackageDirectory 中的其他文件
```

`Platform` 沿用 `TwoStageReleaseBuilder.GetPlatformName`，例如 `Windows64`。发布器复制整个
`OutputPackageDirectory`，不会把本地绝对路径写进 `current.json`。

发布根应与构建输出目录分开，不能是构建输出目录本身，也不能位于构建输出目录内部。发布器会
拒绝路径相同、互相包含、越出发布根或包含重解析点的情况。请避免把发布根直接设为磁盘根目录。

## 4. 打包和本地发布

打开 `TEngine → Build → 打包工具窗口`：

1. 先确定基础包兼容身份 `BasePlayerId`，并在 `UpdateSetting` 中配置固定入口 URL
   和固定主备资源根；这些设置必须在构建 Player 前写入。
2. 选择目标平台，填写资源版本号和新的 `两阶段 Release ID`。每个新发布都应点击“自动”生成新 ID，
   不要复用已登记的构建 ID。
3. 构建与该 `BasePlayerId` 对应的基础 Player，生成最终 AOT 裁剪产物；旧客户端不能直接读取固定入口。
4. 基于该 Player 的 AOT 产物构建匹配的热更 DLL 和 AssetBundle。
5. 勾选 `构建成功后发布到本地目录`，填写 `本地发布根目录`，再执行发布并验证。

该开关默认关闭，并使用 `EditorPrefs` 保存，不写入 `UpdateSetting.asset`。开关打开时必须启用两阶段
更新并正确配置固定入口；不满足时会在构建前失败。`构建 Player` 按钮是独立 Player-only 流程，
不会发布固定入口。

窗口中的流程是：

```text
冻结构建/身份快照
→ 原有 Preflight/DLL/AssetBundle/最小包/Player 流程
→ 确认 BuildStatus.Succeeded
→ 复制到临时 release 目录
→ 文件集、长度、SHA-256 校验
→ 临时目录改名为 releases/{ReleaseId}
→ 原子替换或首次原子移动 current.json
```

构建成功不等于发布成功。窗口会分别显示构建结果、发布结果、发布目录和入口路径；任何构建阶段
失败、最终 AOT 复核失败或发布失败都不会切换 `current.json`。

## 5. 发布事务和失败处理

- 同一身份目录使用独占 `.two-stage-publish.lock`，并发发布会失败。
- 已存在的 release 只有在文件集、文件长度和 SHA-256 全部相同的情况下才复用；内容不同不会覆盖。
- 历史 release 不会自动清理，也不会被后续发布修改。
- 入口存在时使用同目录临时文件和 `File.Replace`；首次入口使用同目录 `File.Move`。
- 不支持原子替换时直接失败，不会退化为删除旧入口后重新写入。
- 临时 release 改名成功后，即使入口提交失败，也会保留完整 release；旧入口继续有效。
- 入口提交前取消只清理本次临时文件/目录；入口提交成功后按成功返回。
- 发布器只操作一个本地发布根，不实现主备服务器上传或远程事务。

当前窗口没有“重试上次发布”入口。如果构建已成功但入口提交失败，完整 release 会保留，且该
`ReleaseId` 已登记，不能再次点击“构建并发布”复用同一 ID。恢复时应先确认保留目录与本次构建产物的
文件集、长度和 SHA-256 完全一致，再使用底层本地发布器复用相同产物完成入口提交；否则生成新的
`ReleaseId` 重新构建发布。后续可单独增加窗口级重试功能，但不需要为此改造构建系统，也不要删除
登记表或覆盖历史 release。

正式部署时应先把同一 release 的完整目录（descriptor、清单、bundle 和其他构建文件）准备到主、
备服务器，并确认两边内容一致，最后再切换两边的 `current.json`。本地发布器不能声称已经完成
这一步。

## 6. 客户端行为

客户端启动时，入口请求会追加每次不同的缓存击穿参数，并发送 `no-cache` 请求头；入口响应限制
为 4 KiB，超过上限会终止。入口和 descriptor 请求不接受重定向。descriptor 先判 `null`，再访问字段，
并要求其 `ReleaseId` 与入口完全相同；随后继续现有的身份、程序集名单和清单 SHA-256 校验。

`PrepareAsync` 完成后，当前会话保存选中的 descriptor、ReleaseId 和主备资源目录，不会重新读取
`current.json`。发布期间服务器改变入口不会影响已经准备好的会话；准备失败后重试才会重新读取入口。
跨过 DLL/metadata 不可逆装载边界后不能切换 release，也不增加离线自动回退。

`EditorSimulateMode` 继续直接使用 `EditorSimulateReleaseDescriptorJson`，不请求 `current.json`。

## 7. 本地文件服务器注意事项

现有 `Tools/FileServer` 是静态服务器辅助工具。本次没有修改其启动脚本或配置。调查结果显示其
`start.bat` 通过 `npm run dev` 启动，默认端口为 8080；若本地测试使用 8081，需要按该工具自身
的配置覆盖端口，并把服务根指向 `PublishRoot`，而不是某一个 `releases/{ReleaseId}` 子目录。

如果使用 loopback HTTP，客户端必须显式勾选 `AllowInsecureLoopbackHttp`。不要把该选项带入正式
环境；正式服务应使用 HTTPS，并对 `current.json` 禁止长期缓存或配置重新验证。

## 8. 迁移和回滚边界

构建和发布工具不会自动修改 `UpdateSetting.asset`、`GameEntry.prefab`、HybridCLR 设置或已有构建资产。
曾使用直接 descriptor 的旧 Player 不能消费固定入口，必须重新构建包含当前主包代码的基础 Player。
`BasePlayerId` 一致表示“新 Player 与对应发布产物使用同一兼容身份”，不表示
升级主包后仍可沿用旧基础包身份。只要 AOT ABI、最终裁剪结果或其他主包兼容边界发生变化，就应分配
新的 `BasePlayerId`，同时保留旧客户端对应的发布目录和入口。

从旧的直接 descriptor Player 迁移时，一次性完成：

1. 确定新的基础包兼容身份，并配置 `BasePlayerId`、固定入口 URL 和固定主备资源根。
2. 使用上述配置构建基础 Player，生成对应的最终 AOT 裁剪产物。
3. 基于该 Player 的身份和 AOT 产物构建匹配的热更 DLL 与 AssetBundle。
4. 在两个服务器准备同一个完整 release 目录。
5. 先用 HostPlayMode 验证入口、descriptor、清单和资源，再将 `current.json` 提供给用户。

发布器没有自动回滚功能。若新 release 已上传但入口尚未提交，旧入口仍然有效；若入口已提交，需由
部署方把 `current.json` 原子替换回已验证的历史 ReleaseId。

## 9. 定向验证

新增测试覆盖：入口 JSON 的 null/损坏/未知版本/未知字段、ReleaseId 边界、固定入口和资源根 URL 规则、
入口缓存参数不污染 descriptor、首次/连续/同内容复用/不同内容拒绝发布、复制中断、入口替换失败、
提交前取消、提交后成功、身份锁、构建失败不调用发布器，以及入口超限、302、404 和请求取消分类。
运行时/编辑器/测试程序集还应在 Unity Test Runner 中执行 EditMode 测试，并在可用环境中完成一次
HostPlayMode 的 A→B 发布验证。
