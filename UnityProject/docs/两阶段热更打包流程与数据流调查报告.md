> 调查范围：`Assets/TEngine/Editor/ReleaseTools/`、`Assets/TEngine/Editor/HybridCLR/`、`Assets/GameScripts/Procedure/`、`Assets/TEngine/Runtime/Core/UpdateSetting.cs`
> 调查日期：2026-09-11
> 结论基于代码逐行核对 + 一次真实构建的日志与产物验证

## 一、总览：打包是一条六阶段流水线

打包编排的唯一核心是 `ReleaseTools.ExecuteBuildWithResult(config, buildPlayer)`（`ReleaseTools.cs:175`）。它按固定顺序推进，**任一阶段失败/取消立即停止下游**：

```
Preflight → Reserve(占用ReleaseId) → Dll → AssetBundle → MinimalPackage(可选) → Player(可选) → Completed
```

各阶段实现集中在 `BuildStageImpl`（可替换，供测试注入替身）：

| 阶段 | 实现入口 | 失败行为 |
|------|----------|----------|
| Preflight | `BuildPreflight.Validate` | 无副作用，直接返回错误列表 |
| Reserve | `TwoStageReleaseBuilder.ReserveReleaseId` | 原子占用 ReleaseId |
| Dll | `BuildDLLCommand.BuildAndCopyDllsWithResult` / `ValidateReusedDllsWithResult` | 抛 `BuildExecutionException` |
| AssetBundle | `ReleaseTools.BuildAssetBundleStage` | 返回 `AbStageOutcome.Fail` |
| MinimalPackage | `ReleaseTools.ProcessMinimalPackageStage` | 抛异常（先校验后删除） |
| Player | `ReleaseTools.BuildPlayerStage` | 以 `report.summary.result` 判定 |
| 收尾复核 | `TwoStageReleaseBuilder.VerifyFinalAotMetadata` | Player 后重新核对 metadata 摘要 |

## 二、入口矩阵（代码/菜单/CLI）

### 2.1 编辑器菜单

| 菜单路径 | 方法 | 行为 |
|----------|------|------|
| `TEngine/Build/打包工具窗口` | `BuildPipelineWindow.ShowWindow` | 打开主窗口 |
| `TEngine/Build/一键打包AssetBundle _F8` | `ReleaseTools.BuildCurrentPlatformAB` | `CreateDefault()` + **强制 `BuildHotFixDll=true`**，不打包 Player |
| `TEngine/Build/一键打包Window` | `ReleaseTools.AutomationBuild` | 完整构建 + 出 Windows Player |
| `TEngine/Build/一键打包Android` | `ReleaseTools.AutomationBuildAndroid` | 同上，Android |
| `TEngine/Build/一键打包IOS` | `ReleaseTools.AutomationBuildIOS` | 同上，iOS |
| `HybridCLR/Build/BuildAssets And CopyTo AssemblyTextAssetPath` | `BuildDLLCommand.BuildAndCopyDlls` | **只编译复制 DLL**，不打包 AB |

### 2.2 CLI（batchmode）

通过 `-executeMethod` 调用，自定义参数走 `-CustomArgs:` 前缀，用 `;` 分隔（`CommandLineReader.cs:47`）：

```bat
:: 只编译复制 DLL（platform 必填）
Unity.exe <Project> -executeMethod TEngine.ReleaseTools.BuildDll -quit -batchmode -buildTarget Android -CustomArgs:platform=Android

:: 只打包 AssetBundle（outputRoot / packageVersion / platform 三者必填）
Unity.exe <Project> -executeMethod TEngine.ReleaseTools.BuildAssetBundle -quit -batchmode -buildTarget Android -CustomArgs:platform=Android;packageVersion=1.02;outputRoot=<BuildRoot>
```

入口方法抛异常时，batchmode 下 Unity 以**非零退出码**结束，可被 CI 捕获。

### 2.3 注意：入口不同，ReleaseId 生成策略不同

| 入口 | ReleaseId 来源 | 是否每次变化 |
|------|----------------|--------------|
| 打包工具窗口 | `EditorPrefs("TEngine_BP_ReleaseId")` 读回上次值 | **不变**（需手点「自动」按钮） |
| 一键打包菜单 / CLI | `BuildConfig.CreateDefault()` | **每次都是新值** |

## 三、配置数据流（唯一的输入源）

### 3.1 BuildConfig（构建期参数）

`BuildConfig` 是编排的输入载体，字段分四组：

- **基础**：`BuildTarget`、`BuildPipeline`、`CompressOption`、`EncryptionType`、`PackageVersion`、`ReleaseId`、`OutputRoot`
- **最小包**：`MinimalPackage`、`RetainTags`
- **高级**：`EnableSharePackRule`、`UseAssetDependencyDB`、`ClearBuildCache`、`VerifyBuildingResult`、`BuildinFileCopyOption`、`FileNameStyle`
- **DLL/Player**：`BuildHotFixDll`、`BuildPlayer`、`PlayerPlatform`、`PlayerOutputPath`

窗口把这些值持久化在 `EditorPrefs`（前缀 `TEngine_BP_`），下次打开自动恢复（`BuildPipelineWindow.LoadSettings/SaveSettings`）。

### 3.2 UpdateSetting（运行时契约，构建期也读）

`UpdateSetting`（`Assets/TEngine/Settings/UpdateSetting.asset`）是**构建期与运行期共用的唯一契约**。关键字段：

| 字段 | 作用 |
|------|------|
| `HotUpdateAssemblies` | 热更程序集名单（含 GameUpdater） |
| `AOTMetaAssemblies` | 需补 metadata 的 AOT 程序集 |
| `LogicMainDllName` | 业务主入口程序集（GameLogic.dll） |
| `AssemblyTextAssetPath` | 业务 DLL 资产目录（`AssetRaw/DLL`） |
| `BootstrapTextAssetPath` | bootstrap DLL 资产目录（`AssetRaw/Bootstrap/DLL`） |
| `BootstrapAssemblyName` | 固定为 `GameUpdater.dll` |
| `BootstrapTag` | 固定为 `BOOTSTRAP` |
| `EnableTwoStageUpdate` | 两阶段总开关 |
| `TwoStageContractVersion` / `BasePlayerId` / `Channel` | 契约身份三元组 |
| `TwoStageReleaseEntryUrl` | 固定 `current.json` URL（运行期先读取 ReleaseId） |
| `TwoStageHostServerUrl` / `TwoStageFallbackHostServerUrl` | 固定主/备资源身份根 |
| `EditorSimulateReleaseDescriptorJson` | 仅编辑器模拟用内联 descriptor |

### 3.3 配置同步链（易踩坑）

`UpdateSettingEditor.OnInspectorGUI` 在
`HotUpdateAssemblies` / `AOTMetaAssemblies` 变化时，把值**剥掉 `.dll` 后缀**写入 `HybridCLRSettings`：

```
UpdateSetting.HotUpdateAssemblies : ["GameUpdater.dll", "GameProto.dll", "GameLogic.dll"]
            │  (UpdateSettingEditor.OnInspectorGUI)
            ▼
HybridCLRSettings.hotUpdateAssemblies : ["GameUpdater", "GameProto", "GameLogic"]
```

而 `BuildDLLCommand` 实际复制时读的是 **`SettingsUtil.HotUpdateAssemblyFilesExcludePreserved`**（HybridCLR 侧，带 `.dll`）。
**两处名单必须一致**，否则会出现「编译了但没复制」或「复制了但没编译」的静默错位。

## 四、构建期数据流（逐阶段）

### 4.1 Dll 阶段：产物的分类与搬运

`BuildDLLCommand.BuildBaseCopyPlan` 生成复制计划，**目标目录由分类决定**：

```
AOT metadata 源: {AssembliesPostIl2CppStrip}/{target}/{dll}
                ├─ 两阶段开启 → {BootstrapTextAssetPath}/{dll}.bytes      (AssetRaw/Bootstrap/DLL)
                └─ 两阶段关闭 → {AssemblyTextAssetPath}/{dll}.bytes       (AssetRaw/DLL)

热更程序集 源:  {HybridCLRData/HotUpdateDlls}/{target}/{dll}
                ├─ dll == BootstrapAssemblyName → {BootstrapTextAssetPath}  (GameUpdater.dll)
                └─ 其它                        → {AssemblyTextAssetPath}     (GameProto/GameLogic)
```

关键保障：
1. **先整体校验后统一复制**（`ValidateSources`）——缺任一必需文件即整体失败，**不允许旧产物掩盖缺失**。
2. `CleanupOwnedStaleArtifacts` 清理「相反分类」的旧副本，防止同一地址被两个 collector 重复收集。
3. AOT metadata 的来源目录 `AssembliesPostIl2CppStrip` **必须由一次真实的 IL2CPP Player 构建产生**——这是整条链路上唯一的硬前置（`scriptingBackend: Standalone = IL2CPP` 已满足）。

### 4.2 AssetBundle 阶段：输出根与产物

输出根由 `ReleaseTools.ResolveOutputRoot` 计算，**两阶段开启时逐层嵌套**：

```
{OutputRoot}/TwoStageReleases/{BasePlayerId}/{Platform}/{Channel}/{PackageName}/{ReleaseId}
```

再叠加 YooAsset 自身的 `{BuildTarget}/{PackageName}/{PackageVersion}`，最终形如：

```
Builds/TwoStageReleases/demo-v1/Windows64/default/DefaultPackage/{ReleaseId}/
  └─ StandaloneWindows64/DefaultPackage/1.0.0/
       ├─ DefaultPackage.version              (版本文件)
       ├─ DefaultPackage_1.0.0.hash           (清单哈希)
       ├─ DefaultPackage_1.0.0.bytes          (清单二进制)
       ├─ DefaultPackage_1.0.0.json           (清单可读)
       ├─ DefaultPackage_1.0.0.report         (构建报告)
       ├─ defaultpackage_assets_assetraw_bootstrap_dll.bundle   ← BOOTSTRAP 标签
       ├─ defaultpackage_assets_assetraw_dll.bundle             ← 业务 DLL
       └─ ...(各资源组 bundle)
```

构建完成后 `VerifyAssetBundleOutputs` 逐个核验 5 个必需文件（版本/哈希/清单二进制/清单JSON/报告）存在且非空。

### 4.3 Bootstrap 隔离校验（两阶段专有）

`TwoStageReleaseBuilder.VerifyBootstrapBundle` 直接读**真实构建报告**，强制：

- Bootstrap updater + 全部 AOT metadata **必须落在同一个 bundle** 内（`bootstrapBundles.Count == 1`）
- 该 bundle **必须带 `BOOTSTRAP` 标签**
- 该 bundle **不得混入业务 DLL**（GameProto/GameLogic）
- 该 bundle 的**依赖闭包**内也不得出现业务 DLL

> 这条校验是「BOOTSTRAP 标签」这一契约的**唯一执法点**。运行期的 `ValidateBootstrapAssetClassification` 是它的对侧复核。

### 4.4 descriptor 生成与 ReleaseId 占用

`TwoStageReleaseBuilder.GenerateAndVerify` 产出 `UpdateReleaseDescriptor`：

```
{
  ContractVersion, ReleaseId, BasePlayerId, Platform, Channel,
  PackageName, PackageVersion, ManifestId, ManifestSha256,
  BootstrapAssembly : { Name, Address, Sha256 },
  BusinessAssemblies: [ { Name, Address, Sha256 }, ... ],
  MetadataAssemblies: [ { Name, Address, Sha256 }, ... ]
}
```

- `Address` == `Name` == 文件名（如 `GameUpdater.dll`），与 collector 的 `AddressByFileName` 对齐
- `Sha256` 是**产物文件内容哈希**，运行期比对
- `ManifestSha256` 是清单二进制的哈希，运行期用于固定清单校验

**ReleaseId 占用是单次的、不可复用的**：构建前在
`{OutputRoot}/TwoStageReleaseRegistry/{BasePlayerId}/{Platform}/{Channel}/{PackageName}/{ReleaseId}.json`
原子写入 `State=Reserved`；成功后改为 `Completed` 并记录 descriptor 路径。
**失败的构建也保留占用**（避免覆盖部分产物）——所以每次打包都必须换新 ReleaseId。

### 4.5 Player 阶段与收尾复核

`BuildPlayerStage` 直接调 `BuildPipeline.BuildPlayer`，以报告结果判定成败。
成功后 `VerifyFinalAotMetadata` 会**再次比对最终 strip 目录**的 metadata 哈希与 descriptor 记录是否一致——防止「AB 前 metadata 与最终基础 Player 不一致」。不一致必须重新复制 DLL、重建 AB。

## 五、运行期数据流（消费侧）

### 5.1 启动链路

```
GameEntry(Awake) → ProcedureLaunch → ProcedureSplash → ProcedureInitPackage
  → ProcedureInitResources → ProcedureTwoStageUpdate → ProcedurePreload
  → ProcedureLoadAssembly → ProcedureStartGame
```

### 5.2 两阶段关键节点

| 阶段 | 关键动作 | 数据来源 |
|------|----------|----------|
| `ProcedureInitPackage` | `TwoStageUpdateCoordinator.PrepareAsync`：下载 `current.json` → 锁定 ReleaseId → 下载 descriptor → 逐字段校验 → 绑定固定清单 | `TwoStageReleaseEntryUrl` |
| `ProcedureInitResources` | 设定 `PackageVersion`；非模拟模式校验主/备源清单哈希并激活 | descriptor.PackageVersion / ManifestSha256 |
| `ProcedureTwoStageUpdate` | 校验 BOOTSTRAP 标签闭包 → 下载 BOOTSTRAP → 注入 metadata → `Assembly.Load(GameUpdater)` → 反射调用 `Entry.RunAsync` → 复核资源就绪 | descriptor + BOOTSTRAP 标签 |
| `ProcedurePreload` | 预加载 `PRELOAD` / `WEBGL_PRELOAD` 标签资源 | 资源包 |
| `ProcedureLoadAssembly` | 按 release 顺序加载业务 DLL，反射调用 `GameApp.Entrance` | descriptor.BusinessAssemblies |

### 5.3 descriptor 校验是「双端一致」契约

`UpdateReleaseDescriptorValidator.Validate` 在**构建期自校验**与**运行期下载后校验**共用同一份代码，逐项精确比对：
`ContractVersion` / `BasePlayerId` / `Platform` / `Channel` / `PackageName` / `ManifestId` / 程序集名单集合。
任何一项不符即拒绝启动——这是防止「旧 descriptor 配新资源」的核心机制。

## 七、发现的问题

### 7.1 【确凿 Bug】descriptor 原子写入超出 Windows MAX_PATH

**现象**：AB 构建成功但整体失败，路径报 `Could not find a part of the path`，目录实际存在。

**根因**：`TwoStageReleaseBuilder.WriteImmutable` 用「同目录临时文件 + 原子改名」写入，临时名追加 `.tmp-{32位GUID}`，把完整路径推过 260 字符上限。

实测长度（本机路径）：

| 路径 | 长度 |
|------|------|
| 目录 | 179 |
| 最终 descriptor `TwoStageRelease_*.json` | 225（合法） |
| **临时文件 `.tmp-{guid}`** | **262（超限）** |
| Windows MAX_PATH | 260 |

**影响面**：同一模式在三处出现，均会踩到——
- `TwoStageReleaseBuilder.WriteImmutable`（descriptor 写入）
- `TwoStageReleaseBuilder.WriteRecordReplacement`（登记表改写）
- `TwoStageUpdateCoordinator.TryWriteTextAtomically`（入口 checkpoint，路径较短，暂未触发）

**修复方向**（择一）：
1. 临时文件改用**短名**（如 `.t{guid前8位}`），压回上限内；
2. 临时文件放到**系统临时目录**再改名（跨卷时需回退为复制）；
3. 缩短输出根（减少 `TwoStageReleases/{BasePlayerId}/{Platform}/{Channel}` 的嵌套层级）；
4. 工程级开启长路径支持（`LongPathsEnabled`），但不可控于代码。

### 7.2 【已补齐】固定入口本地发布链路

打包窗口可以在完整构建成功后，把整个输出发布到
`{PublishRoot}/{BasePlayerId}/{Platform}/{Channel}/{PackageName}/releases/{ReleaseId}`，最后原子提交
`current.json`。客户端只配置一次 `TwoStageReleaseEntryUrl`，不需要在每次构建后修改 Player 配置。
`Tools/FileServer` 仍需把服务根指向 `PublishRoot`，并按实际入口 URL 配置端口。

### 7.3 【顺序守卫缺失】无「必须先出过一次 Player」的提示

`AssembliesPostIl2CppStrip` 是硬前置，但 Preflight 无此检查。直接点「一键构建」会先炸在 DLL 阶段，报「缺少必需 DLL 源文件」，对新人不友好。

### 7.4 【配置陷阱】PlayMode 存在两个独立开关

| 开关 | 存储位置 | 影响的代码 |
|------|----------|-----------|
| 工具栏 Play Mode 下拉 | `EditorPrefs("EditorPlayMode")` | **运行期** `ResourceModuleDriver.PlayMode` |
| `GameEntry.prefab` → ResourceModuleDriver 检视面板 | 序列化字段 `playMode` | **构建期** `BuildPreflight.ValidateResourceDriver` |

两者**不联动**。只切一个会造成「构建预检通过但运行仍是模拟模式」（或反之）。

### 7.5 【口径不一致】metadata 门控两套标准

- `ProcedureLoadAssembly.LoadMetadataForAOTAssemblies`：`#if UNITY_EDITOR return;`（编辑器一律跳过）
- `ProcedureTwoStageUpdate.LoadMetadataAndUpdaterAsync`：仅 `PlayMode == EditorSimulateMode` 时跳过

后果：编辑器 + HostPlayMode 下，两阶段会**去加载并校验 metadata 产物**，而非两阶段路径直接跳过。因注入在编辑器是空操作（`HybridCLR.RuntimeApi.LoadMetadataForAOTAssembly` 在 `UNITY_EDITOR` 下无条件返回 `OK`），不产生错误，但属多余动作且口径分裂。

### 7.6 【已修复】打包窗口在 OnGUI 内执行长任务

`BuildPipelineWindow` 原先在按钮回调（仍在滚动视图分组内）同步执行构建，长同步操作期间 Unity 继续派发 IMGUI 事件，冲掉 GUILayout 分组栈，恢复后 `EndScrollView` 报
`EndLayoutGroup: BeginLayoutGroup must be called first`。
已改为 `EditorApplication.delayCall` 延后执行，并在构建期间禁用按钮。

### 7.7 【健壮性】构建日志集合的并发风险

构建期间窗口重绘会遍历 `_buildLogs`，而 `Application.logMessageReceived` 回调会向其追加。目前日志回调均在主线程，未触发异常；若未来出现非主线程日志，会抛 `Collection was modified`，表现为同类 GUI 报错。建议加锁 + 绘制时取快照。

## 八、附：完整操作链（HostPlayMode 真机验证）

```
① 出一次 Player（生成 AOT 裁剪产物）
   TEngine/Build/打包工具窗口 → 底部「构建 Player」
   （或菜单 TEngine/Build/一键打包Window）

② 编译复制 DLL + 打 AB + 生成 descriptor
   同一窗口：
     - 基础设置：目标平台 / 资源版本号 / 两阶段 Release ID（每次点「自动」换新）
     - 「热更DLL设置」勾选「构建前编译热更DLL」
     - 点「构建 AssetBundle」
   产物：Builds/TwoStageReleases/.../{ReleaseId}/StandaloneWindows64/DefaultPackage/{版本}/

③ 配置一次固定入口（TEngine/Settings/TEngine UpdateSettings）
   - TwoStageReleaseEntryUrl       = http://127.0.0.1:8081/demo-v1/Windows64/default/DefaultPackage/current.json
   - TwoStageHostServerUrl         = http://127.0.0.1:8081/demo-v1/Windows64/default/DefaultPackage
   - TwoStageFallbackHostServerUrl = http://127.0.0.1:8082/demo-v1/Windows64/default/DefaultPackage
   - AllowInsecureLoopbackHttp    = 勾选

④ 起服务器（Tools/FileServer）
   - 服务根必须 = 本地发布根目录 PublishRoot
   - 端口改 8081（默认 8080 不匹配）

⑤ 切模式（两个开关都要改）
   - Unity 工具栏 Play Mode → HostPlayMode（写 EditorPrefs）
   - GameEntry.prefab → ResourceModuleDriver → 运行模式 → HostPlayMode（写序列化字段）

⑥ 清缓存后 Play
   TEngine/Open Folder/Persistent Data Path → 删除 YooAsset 缓存与 two-stage-entry/
```

**已知第 ② 步当前会失败**，原因是 7.1 的 MAX_PATH bug，需先修复。
