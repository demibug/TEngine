# 原工程武器合成实现调查

> 调查日期：2026-08-28  
> 调查范围：原工程 `src` 重建代码、原始 JavaScript bundle、武器配置与武器界面资源  
> 结论性质：静态源码与混淆 bundle 解码后的行为还原；本次未修改业务代码

## 1. 结论先行

原工程的“武器合成”本质上不是“两把不同武器合成一把新武器”的配方系统，而是：

1. 以 `weaponId` 为 key 累计武器碎片。
2. 从 `weapon.json` 读取该武器的 `fragmentNum` 作为合成阈值。
3. 累计总碎片每跨过一次阈值，就自动形成一件完整武器，并把该 `weaponId` 放入“新武器”提示队列。
4. 原始碎片总数不会在形成武器时扣除；它保存在玩家数据中，完整武器数量通过 `floor(totalFragments / fragmentNum)` 推导。
5. 启动或刷新时，运行时把总碎片拆成若干个完整堆和一个未完成堆。只有完整堆能装备到武器栏，未完成堆只显示进度。

因此，最准确的一句话是：

> 同一 `weaponId` 的碎片达到配置阈值后自动解锁武器；这是“碎片累计解锁”，不是跨武器配方合成。

## 3. 数据模型

### 3.1 武器配置

`weapon.json` 共登记 44 个武器配置，`type` 分布为弓 10 个、矛 10 个、刀 11 个、剑 13 个。配置字段 `fragmentNum` 是单个武器所需碎片数。

当前数据中的阈值与品级对应关系为：

| `rarity` | `fragmentNum` | 配置数量 | 含义 |
|---:|---:|---:|---|
| 0 | 1 | 4 | 1 个碎片形成 1 件武器 |
| 1 | 2 | 8 | 2 个碎片形成 1 件武器 |
| 2 | 3 | 8 | 3 个碎片形成 1 件武器 |
| 3 | 4 | 13 | 4 个碎片形成 1 件武器 |
| 4 | 5 | 11 | 5 个碎片形成 1 件武器 |

例如：

- `id=0` 的“短弓”是 `rarity=0`，`fragmentNum=1`。
- `id=1` 的“长弓”是 `rarity=1`，`fragmentNum=2`。
- `id=3` 的“角弓”是 `rarity=2`，`fragmentNum=3`。

### 3.2 玩家持久化数据

解码后的 `PlayerData` 维护以下几个与武器直接相关的字段：

| 字段 | 形态 | 作用 |
|---|---|---|
| `weaponFragments` | `[[weaponId, totalCount], ...]` | 每个武器 ID 的碎片总数，是合成进度的持久化来源。 |
| `_newWeaponIds` | `[weaponId, ...]` | 新形成的完整武器提示队列；同一个 ID 可以出现多次。 |
| `_equip` | 长度为 12 的数组 | 武器栏槽位到运行时碎片堆 `id` 的映射，空槽为 `-1`。 |

`PlayerData.getWeaponFragmentCount(id)` 查找 `weaponFragments` 中的 `[id, count]`；`setWeaponFragments(id, delta)` 对该总数做增量写入；`addNewWeaponId(id)` 追加提示队列。相关实现位于 [`bundle.js`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/origin_project/js/bundle.js:8733>) 的 `PlayerData` 方法区域。

这里的 `count` 是“该武器 ID 的累计总碎片”，不是当前未合成余数。因此合成完成后不会把它重置为 0，也不会只保留余数。

### 3.3 运行时碎片堆对象

bundle 中的 `s7` 是一个运行时碎片堆/武器项对象，关键字段可还原为：

| 语义 | 混淆字段 | 说明 |
|---|---|---|
| 武器 ID | `weaponId` | 指向 `weapon.json.id`。 |
| 当前堆数量 | `oc` | 当前显示的碎片数。 |
| 最大堆数量 | `lc` | 等于该配置的 `fragmentNum`。 |
| 运行时项 ID | `id` | 用于装备槽位引用和拖拽识别。 |
| 装备槽位 | `yc` / `fc` | 未装备为 `-1`。 |
| 是否完整 | `isComplete` | `oc >= lc`。 |
| 是否已装备 | `dc` | 装备槽位大于等于 0。 |

因此，“完整武器”在运行时不是另一种完全独立的数据类型，而是 `oc` 已达到 `lc` 的完整碎片堆。`WeaponScene` 将其作为可装备对象处理。

## 4. 核心合成算法

原始 bundle 中的武器碎片管理器是 `nP`，单例实例在后续逻辑中以 `qx` 使用。核心方法 `setWeaponFragments` 位于 [`bundle.js`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/origin_project/js/bundle.js:7969>)，行为可以还原为：

```js
setWeaponFragments(weaponId, delta) {
    const config = weaponConfig.get(weaponId);
    const required = config ? config.fragmentNum : 1;

    const beforeTotal = player.getWeaponFragmentCount(weaponId);
    const beforeCompleted = Math.floor(beforeTotal / required);

    // 只改变持久化碎片总数，不在此处扣除 required。
    player.setWeaponFragments(weaponId, delta);

    const afterTotal = beforeTotal + delta;
    const afterCompleted = Math.floor(afterTotal / required);

    for (let i = 0; i < afterCompleted - beforeCompleted; i++) {
        player.addNewWeaponId(weaponId);
    }
}
```

可以得到四个确定结论：

- 合成匹配条件只有 `weaponId`；没有“来源武器 ID + 目标武器 ID”的组合判断。
- 阈值由配置的 `fragmentNum` 决定，而不是写死为固定碎片数。
- 一次增加很多碎片时，可以跨过多个阈值，循环会追加多个 `newWeaponIds`。
- 负数增量用于回收碎片；该循环不会因为负数而新增武器，但会降低后续由总数推导出的完整武器数。

### 4.1 数值例子

以 `id=1` 的“长弓”为例，`fragmentNum=2`：

| 操作 | 持久化总数 | `floor(total / 2)` | 新增提示 |
|---|---:|---:|---:|
| 初始 | 0 | 0 | 0 |
| 获得 1 个碎片 | 1 | 0 | 0 |
| 再获得 1 个碎片 | 2 | 1 | 1 |
| 再获得 3 个碎片 | 5 | 2 | 1 |

如果初始为 0、一次性获得 5 个长弓碎片，则会一次追加 2 个 `newWeaponIds`，持久化总数仍为 5；刷新背包后表现为 2 个完整堆和 1 个 `1/2` 的未完成堆。

## 5. 启动时如何把总碎片还原成武器堆

碎片管理器的初始化方法 `Sc()` 位于 [`bundle.js`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/origin_project/js/bundle.js:7769>)。它遍历玩家保存的 `[weaponId, totalCount]`，对每个配置执行：

```text
required   = weaponConfig[weaponId].fragmentNum
fullCount  = floor(totalCount / required)
remainder  = totalCount % required

创建 fullCount 个：current = required，属于完整武器堆
如果 remainder > 0，再创建 1 个：current = remainder，属于未完成堆
```

每个运行时堆都会登记到三组索引中：

- 按 `type` 索引，用于按武器类别展示和筛选。
- 按 `weaponId` 索引，用于计算某个武器的完整数量、寻找装备对象。
- 按运行时 `id` 索引，用于拖拽、装备槽位和界面项定位。

之后 `xc()` 根据玩家 `_equip` 中保存的运行时项 ID 恢复装备状态；恢复装备时只接受 `isComplete` 且当前未装备的堆。这个限制说明未完成碎片堆不能直接装到武器栏。

## 6. 一条完整的获得—合成—提示链路

```text
战斗奖励/其他奖励
    └─ 选择 weaponId 与本次 fragmentNum
         └─ qx.setWeaponFragments(weaponId, delta)
              ├─ 增加 PlayerData.weaponFragments 的累计总数
              ├─ 计算 floor(total / 配置.fragmentNum) 的变化
              └─ 每新增一件完整武器，追加 PlayerData._newWeaponIds
                   └─ WeaponScene 刷新
                        └─ NewWeaponDialog 显示“新武器”与数量
                             └─ 点击“收下”
                                  └─ 清空 _newWeaponIds，并刷新界面
```

### 6.1 战斗奖励入口

bundle 的战斗奖励逻辑在 [`bundle.js`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/origin_project/js/bundle.js:20178>) 附近会先取得一个武器碎片结果；结果需要满足 `weaponId >= 0` 且碎片数大于 0，然后调用 `qx.setWeaponFragments(...)`。选择结果的随机/候选逻辑在同一管理器的 `tu()` 中，因 bundle 混淆较重，具体概率和候选权重不作为本报告的合成规则结论。

bundle 还保留了 GM/调试入口，会随机选择可用武器并调用同一个 `setWeaponFragments`；这进一步说明奖励入口和调试入口共用同一套合成阈值逻辑。

### 6.2 新武器弹窗不是合成按钮

`WeaponScene` 初始化/刷新时读取 `PlayerData.getNewWeaponIds()`，按 `weaponId` 统计重复项，再把名称和数量传给 `NewWeaponDialog`。对应界面资源 [`NewWeaponDialog.lh`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/origin_project/dialog/NewWeaponDialog.lh>) 的按钮文案是“收下”。

点击“收下”后的 bundle 逻辑会调用 `clearNewWeapons()` 并刷新武器界面；可见代码没有把 `fragmentNum` 从 `weaponFragments` 中扣除。因此弹窗是“领取/确认新武器提示”，不是实际执行合成扣除的地方。

## 7. 装备、查看与回收

### 7.1 装备

装备方法 `qc()` 位于 [`bundle.js`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/origin_project/js/bundle.js:7923>)：

- 通过运行时项 ID 找到碎片堆。
- 要求该堆 `isComplete`。
- 如果它已经在其他槽位，先解除旧槽位。
- 如果目标槽位已有完整武器，则先解除目标项。
- 更新运行时装备槽位，并写入 `PlayerData._equip`。

所以界面上的 `0/fragmentNum`、`1/fragmentNum` 等进度展示，并不意味着可以把半成品装备上去；只有达到阈值后的完整堆才进入装备链路。

### 7.2 回收

回收由 [`RecycleWeaponDialog.lh`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/origin_project/dialog/RecycleWeaponDialog.lh>) 和 bundle 中的 `RecycleWeaponDialog` 类共同完成。其行为是：

1. 界面只提供白、绿、蓝三档品级选择，即 `rarity=0/1/2`；代码会跳过更高品级。
2. 汇总所有未装备的武器碎片堆：完整堆按 `lc=fragmentNum` 计，未完成堆按当前 `oc` 计。
3. 金币倍率按品级为白色 1、绿色 2、蓝色 3。
4. 点击“一键回收”后，对每个汇总项调用 `player.setWeaponFragments(weaponId, -fragments)`，再调用 `qx.refresh()` 重建运行时堆。

回收是“碎片总数减法”，不是合成的逆向配方；回收确认代码位于 [`bundle.js`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/origin_project/js/bundle.js:64689>) 附近。实现恢复时需要额外测试“已弹出但尚未点击收下时发生回收”的提示队列一致性，因为回收确认本身可见的是扣减总数和刷新背包，并不直接调用 `clearNewWeapons()`。

## 8. 与当前 `src` 中“单位合成”的区别

当前重建代码里的 [`UnitMergeService.js`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/src/units/UnitMergeService.js>) 实现的是单位合并：要求同阵营、同 `unitText`、同等级，然后升级目标单位并移除来源单位。这不是武器合成。

[`WeaponManager.js`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/src/weapons/WeaponManager.js>) 和 [`WeaponFactory.js`](<D:/UnityProject/MyTEngine/TEngine/Origin/reconstructed-project/src/weapons/WeaponFactory.js>) 目前只负责：

- 按武器类型/索引创建运行时武器对象；
- 把武器挂到单位；
- 管理运行时武器集合和默认装备。

它们没有实现 `weaponFragments`、`fragmentNum`、`_newWeaponIds` 或回收扣减。因此如果只阅读 `src/weapons`，会看不到原工程完整的武器合成逻辑；需要以原始 bundle 的 `nP/qx` 碎片管理器和 `PlayerData` 持久化方法为准。

## 9. 对 Unity 侧恢复的最小实现建议

以下是根据原工程行为提炼出的移植契约，不是原工程新增代码：

1. 以 `Map<weaponId, totalFragments>` 作为唯一持久化事实来源；不要把“已合成数量”和“剩余碎片”分别保存成两套容易分叉的数据。
2. 合成阈值始终从武器配置读取：`required = config.fragmentNum`。
3. 每次增量前后比较 `floor(total / required)`，差值为正时逐件派发 `NewWeaponCreated(weaponId)` 事件。
4. 背包视图按 `fullCount` 个完整项加至多一个余数项重建；完整项才允许装备。
5. 新武器提示单独保存为队列或计数表；点击确认只清提示，不扣碎片。
6. 回收复用同一个碎片增量入口传入负数，并明确处理装备限制和提示队列一致性。
7. 不要把 `UnitMergeService` 的“同单位升级”规则套到武器碎片上；两者是不同的业务模型。

## 11. 仍需动态验证的部分

原始 `bundle.js` 的武器碎片选择器 `tu()` 仍有较多混淆符号。静态分析已经足以确认“如何累计、何时形成完整武器、如何持久化和回收”，但以下内容不宜仅凭当前 bundle 解码结果下定论：

- 不同战斗/关卡下具体会掉落哪些 `weaponId`；
- 候选武器的随机权重和保底规则；
- 回收发生在新武器提示尚未确认时，提示队列与总碎片减少后的最终交互表现。

这些不确定项不影响本报告的核心结论：合成判定统一收敛在 `setWeaponFragments` 的阈值跨越计算上。
