## 2. 结论摘要

当前阴影系统由两层组成：

1. 单位层：根据画质在“脚下假阴影”和“角色实时投影”之间切换。
2. 主光管线层：中高画质下使用主光阴影图；Game Camera 在满足条件时走 SLG 投影分支，SceneView 或特殊场景走标准 Universal 分支。

当前系统的主要优点是实现清晰、低画质有明确降级、所有单位共享一张主光阴影图，并且只有一个 cascade，避免了每单位阴影图和多级 cascade 的额外成本。

主要风险是：

- 中高画质下每个可参与阴影的 SkinnedMeshRenderer 都会额外进入 ShadowCaster 绘制。
- Medium 软阴影在接收端使用约 9 次阴影比较采样，成本与屏幕接收阴影的像素数量相关。
- 主城单位逻辑每帧遍历已加载单位并执行一次阴影状态检查，已加载数量很大时会产生额外 CPU 成本。
- `CustomShadow` 是全局状态，皮肤展示或英雄捕获可能影响其他 Game Camera 的阴影分支。
- 当前 SLG 逻辑改动了 URP 包和阴影 Shader，正式迁移时不能直接修改 `Library\PackageCache`。

对迁移的建议是：先在目标工程实现“标准 URP + 假阴影/实时阴影双模式”，完成性能和资源闭环；只有标准 URP 无法满足主城镜头的阴影质量时，再迁移 SLG 包改动。

## 5. 技术优点

### 5.1 画质降级路径明确

低画质关闭角色实时投影，使用脚下假阴影；中高画质恢复实时投影。对移动端和低端设备来说，这是比“所有设备都实时投影”更稳妥的基础策略。

### 5.2 阴影图是共享资源

所有角色共享主光阴影图，不会因为单位数量增加而为每个角色分配一张 1024 或 2048 阴影图。单位数量增加的主要代价是 ShadowCaster 绘制复杂度，而不是阴影图数量直接增加。

### 5.3 一个 cascade 降低了绘制复杂度

当前 High、Medium、Low 都是 1 cascade。相比 2 或 4 cascade：

- 阴影投射绘制次数更少。
- 阴影图分配和切片管理更简单。
- 不存在多 cascade 接缝和级联选择成本。

代价是近处和远处共享同一张阴影图，近处精度、远处覆盖范围只能折中。

### 5.4 实时角色阴影表现更正确

角色移动、旋转和动画变化时，实时阴影能反映动态轮廓；假阴影只能提供固定的脚下接触感，不能正确表现长阴影、障碍物遮挡和方向变化。

### 5.5 SLG 对固定主城镜头有针对性

SLG 根据 Game Camera 的透视视锥生成阴影矩阵，目标是把有限的阴影图精度集中在实际镜头可见区域。对于主城这种镜头相对固定、需要保证角色和地面观感的场景，这种定制有价值。

## 6. 技术缺点和风险

### 6.1 中高画质会增加一次角色阴影绘制

打开实时投影后，角色除了正常颜色 pass，还会进入 ShadowCaster pass。每个角色的 SkinnedMesh 顶点和子网格复杂度都会影响阴影阶段 GPU 和渲染提交成本。

影响更大的不是“总人口”，而是：

- 当前相机可见且参与阴影裁剪的单位数。
- 每个单位的 SkinnedMeshRenderer 数量。
- 每个 Renderer 的顶点、三角形和材质子网格数量。
- 角色是否一直处于动画和骨骼更新状态。

### 6.2 Medium 软阴影是接收端的全屏成本

当前 Medium 软阴影质量为 2，对单个接收阴影的像素执行约 9 次阴影比较采样。主城地面面积较大时，该成本与屏幕分辨率和接收阴影像素数量相关，并不只取决于单位数量。

如果排查性能，不能只关闭所有角色投影，还要单独比较“软阴影开/关”，否则容易漏掉接收端成本。

### 6.3 单级阴影图存在精度和稳定性折中

2048 阴影图只有一个 cascade，覆盖范围越大，单位面积可使用的 texel 越少，可能出现：

- 远处阴影过早消失。
- 近处锯齿或闪烁。
- 阴影随相机移动产生稳定性问题。
- 主城范围扩大后，需要在阴影距离和近处质量之间做取舍。

SLG 只能改善投影矩阵的利用方式，不能消除单张有限分辨率阴影图的根本限制。

### 6.4 `CustomShadow` 全局状态容易产生跨场景影响

当前 `CustomShadow` 是全局布尔值，不绑定具体 Camera，也不表达多个使用者之间的所有权关系。多个皮肤展示、英雄捕获或特殊相机同时存在时，最后一次 `OnEnable/OnDisable` 可能覆盖其他功能的状态。

### 6.5 Game 和 SceneView 使用不同分支，调试结果不一致

编辑器 SceneView 走 Universal，游戏镜头走 SLG。编辑器中看到的锯齿、偏移和柔和程度不能直接代表正式 Game Camera 的实际表现；编辑器性能也可能因为同时渲染 SceneView 和 GameView 而偏高。

### 6.6 自定义 URP 包有升级和维护成本

当前实现包含：

- `UniversalRenderPipelineAsset` 的 ShadowStyle 和 ShadowRange 扩展。
- `MainLightShadowCasterPass` 的分支改动。
- `SlgShadow` 矩阵生成。
- `Shadows.hlsl` 中的关键字和全局矩阵。

这些改动不是标准 URP 14.0.12 的默认能力。若直接修改 `Library\PackageCache`，重新导入包、切换机器或升级 Unity 后可能丢失。正式实现必须放入可版本控制的包源码、私有 Registry 或 embedded package。

## 7. 性能模型

可以把当前系统每帧阴影成本抽象为：

```text
总阴影成本
≈ ShadowCaster CPU 裁剪和提交
  + 参与投影角色的顶点/三角形绘制
  + 阴影图的光栅化填充
  + 接收阴影像素 × 软阴影采样次数
  + 已加载单位的每帧 C# 状态检查
```

各部分的扩展规律如下：

| 成本 | 主要变量 | 当前系统表现 |
|---|---|---|
| ShadowCaster 绘制 | 可见投影角色数、网格复杂度 | 中高画质全部开启，最需要关注 |
| 阴影图填充 | 投影物在阴影图中的覆盖面积 | 分辨率固定，但近景大角色会增加填充压力 |
| 阴影接收 | 屏幕像素数、软阴影采样次数 | Medium 约 9 次，High 约 16 次 |
| 阴影图显存 | 分辨率、深度格式、临时 RT | 2048² 的 16-bit 深度理论数据量约 8 MiB，实际依平台格式可能更高 |
| 单位层 CPU | 已加载单位总数 | 每帧查询画质并检查状态 |
| 编辑器额外成本 | SceneView 和 GameView 是否同时渲染 | 当前调查会话中两类相机都存在 |

注意：`context.DrawShadows()` 是一次针对多个投影者的阴影绘制入口，不等于每个单位一个 DrawCall。实际内部绘制数量仍然会受到 Renderer、材质子网格、Shader pass 和 SRP Batcher 条件影响。

### 数量风险判断

以下是压测起始建议，不是代码保证的硬阈值：

- 约 20 个可见角色、每个 1～2 个 SkinnedMeshRenderer：PC 上通常不是主要风险点，但 Editor 不能代表正式包。
- 约 50 个可见且持续动画的角色：应开始观察 `MainLightShadow` GPU 时间和 ShadowCaster 三角形数。
- 约 100 个以上可见实时投影角色：建议引入距离分层、LOD 或实时投影预算，不建议无条件全部投影。
- 数百个已加载但屏幕外的单位：重点检查主城 C# 每帧遍历，不要只看 GPU ShadowCaster。

移动端需要单独判断。2048 阴影图和软阴影即使角色数量不大，也可能因为 GPU 带宽、阴影采样和填充率成为瓶颈。

## 11. 验收标准

### 功能验收

- 低画质下 `NPC_shadow` 显示，角色 SkinnedMesh 不投射主光阴影。
- 中高画质下 `NPC_shadow` 隐藏，角色实时投影开启。
- 画质切换后所有 Renderer 状态一致，没有一部分单位残留旧状态。
- 单位加载、卸载、对象池复用后阴影状态正确。
- 皮肤展示或英雄捕获关闭后，不会永久污染主城 Game Camera 的阴影分支。
- SceneView 和 Game Camera 的预期分支符合设计。
- 真机打包后 Shader Variant 完整，不出现粉色材质或阴影关键字缺失。

### 性能验收

- 在目标设备上比较 0、20、50、100 个实时投影单位的帧时间变化。
- ShadowCaster 时间随投影单位数增长可控。
- 关闭软阴影后，接收端 GPU 时间有可解释的下降。
- 低画质假阴影的透明 Overdraw 不成为新的主要瓶颈。
- 主城单位 C# 每帧遍历不会随已加载人口无限增长到不可接受。
- 编辑器性能和正式 Player 性能分别记录，不混用结论。
